# 14A: открытие SQLite без изменения отвергаемой базы

20 октября 2026. Это проверка механизма допуска, не завершённая приёмка 14A.

Ревью выявило: обычное `SQLITE_OPEN_READ_ONLY` может менять WAL read marks в `-shm`. Проверка `immutable=1` не заменяет чтение логического состояния: она видит main-файл и пропускает схему, которая находится только в WAL. Поэтому main-версия 0 сама по себе не доказывает пустую базу.

Librarian проверил установленный `rusqlite 0.40.2` / bundled SQLite `3.53.2` (`libsqlite3-sys 0.38.2`) на отдельных синтетических файлах с точной текущей `schema.sql`.

| Состояние | `mode=ro&readonly_shm=1` |
| --- | --- |
| Main version0, schema7 полностью в WAL | Версия7 и таблица tasks прочитаны; DB/WAL/SHM побайтно прежние |
| Main version0, legacy version6 в WAL | Версия6 прочитана; DB/WAL/SHM побайтно прежние |
| Существующий пустой SHM | Версия7 восстановлена в памяти из WAL; файлы не изменились |
| Отсутствующий SHM | CANTOPEN; DB/WAL прежние, SHM не создан |
| Обычный READ_ONLY для старой схемы | Версия6 прочитана, но SHM изменился |
| `immutable=1` для WAL-only схемы | Видна только main-версия0; WAL-схема не видна |

Опоры в закреплённом `sqlite3.c`: `unixOpenSharedMemory` около строки45218 открывает SHM только для чтения; обработка `SQLITE_READONLY_CANTINIT` около70105 использует WAL-index в памяти. Windows VFS также содержит `readonly_shm`, но на Windows этот путь здесь не запускался. Параметр найден в исходнике VFS, а не в публичном перечне URI-параметров: смена bundled SQLite требует повторения регрессии.

Независимый Plan Reviewer предложил временный exclusive admission на одной connection как альтернативу и отдельно потребовал доказать отсутствие recovery/sidecar writes. Проверенный readonly EXCLUSIVE-вариант при отсутствующем SHM дал IOERR_SHMLOCK. Добавлять его, собственный WAL parser, VFS или копию хранилища без необходимости не принято.

Выбранное направление — один WAL-aware read-only preflight с `readonly_shm=1` вместо пары immutable/обычного readonly. Отсутствующие или непригодные вспомогательные файлы не объявляются старой схемой: это ошибка открытия без автоматической записи или восстановления. Штатное хранилище Ambient использует DELETE journal; данный путь не обещает восстановление произвольной внешне изменённой WAL-базы.

Исполнитель 14A добавляет регрессии старой и текущей схемы только в WAL, пустого/повреждённого/отсутствующего SHM, сверку байтов и проверяет обычный Store reopen. Окончательные результаты, ограничения конкуренции и проверки ошибок войдут в его handoff. Исследование само по себе не заменяет эти тесты и полную проверку приложения.

## Уточнение после проверки живого соединения

В старом тесте дополнительная raw `rusqlite::Connection` держала writable WAL в том же процессе. SQLite повторно использует общий `unixShmNode`: параметр readonly_shm действует при открытии нового узла, но не превращает уже существующий writable mapping в readonly. В этом искусственном embedding-сценарии меняется один байт SHM. Это известное ограничение, а не исправленная гарантия.

Scout проверил production-владение: `Store.connection` закрыта; все Core/bridge handles создаются через Store::open и переводят БД в DELETE journal. Даже удержанный model operation `Arc<StoreSlot>` сохраняет такое соединение. Другого production SQLite-владельца и способа переключить соединение в WAL через публичный app API нет. Предыдущая версия приложения работает отдельным процессом.

Независимый Plan Reviewer и управляющий приняли замену модели теста: отдельный **тестовый** процесс держит старую WAL-базу открытой; после ready он не выполняет SQL, а родитель вызывает настоящий Store::open и проверяет UnsupportedSchema плюс полную неизменность DB/WAL/SHM до остановки дочернего процесса. Случай закрытого/crashed writer остаётся отдельно. Same-process repro сохраняется в доказательствах, без заявления о его исправлении.

Гарантия относится к нынешнему app-owned Store path. Произвольный embedder с прямым raw writable SQLite в том же процессе в неё не входит. Появление такого production-владельца требует повторного решения. Production helper, VFS и эвристика immutable не добавляются. Финальная приёмка ждёт живого отдельного процесса и focused review.
