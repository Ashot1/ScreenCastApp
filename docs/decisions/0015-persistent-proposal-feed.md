# ADR-015: постоянная лента предложений и текущее обсуждение

**Поправка 24A (21 октября 2026):** при включённом плагине с одобренными инструментами одно действие помощи может отправить до 5 POST модели и до 8 вызовов инструментов ([ADR-021](0021-plugins-layer.md)); без таких плагинов запрос прежний, ровно один.

Статус:08B реализован и принят локально20 октября2026. Verify8 tooling/154 Rust/71 Swift, расширенный Swift105 с настоящим ASR, Clippy/build/signatures/review — PASS. Сохранена контрольная сборка Ambient-feed-08b.app. Реальные UI/High Fast и полная08 остаются открытыми. [Доказательства](../../target/verification/08b/verification-summary.json).

## Problem Statement

08A показывает один временный результат. После следующего ответа или перезапуска прежняя помощь теряется; разные действия одного дела нельзя держать рядом. Для будущих напоминаний также нужен один постоянный объект предложения, а не повторный показ случайного ответа модели.

## Solution

В существующем Core/SQLite хранится одна текущая область помощи на дело: выбранные основания, атрибутированные пары вопроса и ответа, активные предложения и их закрытие. Краевая лента и общая панель показывают одни объекты. Все действия доступны у края; детали раскрываются и прокручиваются там же. Помощь пока запускается явно через прежний High Fast путь. Сценарии не зашиваются в код.

Сохраняется только необходимое текущее обсуждение. Архива ответов, второй памяти, отдельного чата, нового планировщика и автоматического извлечения подтверждённых фактов нет. Сгенерированный текст не становится пользовательской заметкой, Evidence или планом.

## User Stories

1. Несколько разных действий одного дела остаются отдельными карточками.
2. Повторный анализ обновляет существующее действие, сохраняя его закрытие.
3. После перезапуска я нахожу прежние предложения и могу продолжить актуальное обсуждение.
4. Вся лента доступна у края экрана; переход в общую панель необязателен.
5. Появление новых карточек не отнимает фокус, не переставляет редактируемую карточку и не меняет адресата ответа.
6. Я отвечаю текстом или существующим голосовым путём10A; отправляется только проверенный мной текст.
7. Я вижу устаревшие основания и не получаю разрешение на действие из сохранённого старого ответа.
8. Если выбираю новый контекст, заранее вижу, что успешный ответ заменит обсуждение и покажет предложения заново.
9. Ошибка запроса не уничтожает прежнюю ленту или мой неотправленный текст.
10. Забытое или исключённое сведение не возвращается через сохранённый вопрос, rationale или непрoцитированный контекст.
11. Закрытие убирает карточку пока; «Не актуально» сохраняет существующее подавление инициативы по делу.
12. При достижении предела приложение объясняет отказ, а не скрывает часть предложений и не отправляет дополнительные запросы.

## Implementation Decisions

### Владение и версии

Один прежний Store владеет областью помощи, проверкой оснований и журналом расходов. Native владеет геометрией, раскрытием деталей, фокусом и одним независимым черновиком. Coordinator, model transport, источник credentials и подтверждённая остановка сохраняются.

После принятой14A новая schema8 заменяет7 без миграции, сброса или sidecar-хранилища. Старая БД возвращает UnsupportedSchema без записи. Model ABI4 заменяет3; memory3/auth1/local-source1/Codex1 сохраняются. Существующий единичный result/receipt не остаётся вторым публичным владельцем помощи: его процессные детали допуска используются только внутри отправки. Старые model v3 exports удаляются.

В долговечной строке tasks находится отдельная положительная `assistant_workspace_revision`. Она не входит в TaskVersion и не повышает `task.revision`. Любая успешная публикация или очистка области повышает её в той же транзакции, включая пустой результат. Значение не сбрасывается после удаления области. Это закрывает гонку «пусто → новое обсуждение → снова пусто → поздний старый ответ». Переполнение счётчика — отказ без записи.

ProposalId выделяется Core через SQLite INTEGER PRIMARY KEY AUTOINCREMENT, не переиспользуется; очистка не сбрасывает sqlite_sequence. У предложения есть task ID, content revision, kind, message, rationale, типизированные citations, optional StepId и visibility. Revision меняется при изменении содержимого/оснований/типа/StepId; перестановка ответа и visibility его не меняют. Модель не задаёт revision или visibility.

Workspace revision защищает полный набор и контекст. ProposalId/content revision защищают адресата черновика. TaskVersion и все source settings fences защищают основания. Ни один из этих счётчиков не доказывает полезное новое событие или продолжение работы.

### Минимальные сохраняемые данные

Область содержит TaskVersion, точный список выбранных EvidenceId (не более32), типизированные Git/Codex source fences14A, текущие пары диалога и предложения. Содержимое заметок, источников, плана, проверок и useful references не копируется в отдельный архив: Core заново читает их из прежней памяти при точном совпадении TaskVersion и fences. Весь первоначально отправленный контекст остаётся зависимостью, включая сведения, которых нет в citations ответа.

Зависимости сохраняются явно вместе с областью. Очистка только process snapshot после транзакции, как в08A, недостаточна: удаление постоянных производных выполняется внутри той же транзакции изменения памяти/настроек.

Пары диалога хранят вопрос модели и точный пользовательский ответ раздельно, а также исторические ProposalId/content revision вопроса. Эта историческая ссылка не требует живой карточки и не разрешает действие. Ответ пользователя не становится подтверждением предпосылок вопроса.

ID новой пары: `reply:<task-id>:<workspace-revision-before-publication>:<pair-index>`. Preview вычисляет его без записи. Пара сохраняется только с успешной публикацией и дальше сохраняет этот ID. Неиспользованный preview ничего не резервирует. ID дела не переиспользуется благодаря существующим tombstones; workspace revision долговечна. Process-local request ID для постоянной идентичности не используется.

Citations сохраняются как типизированные ссылки на task/note/source/step/check/reply, а не дублированные тексты оснований. Модель выбирает только IDs точного preview. У ссылки на reply отдельная атрибуция; её нельзя интерпретировать как EvidenceId. Ни receipt, session epoch, credential, High capability, полный HTTP body, ни прежний serialized preview в SQLite не сохраняются.

Область без активных предложений удаляется вместе с парами. Монотонная workspace revision остаётся. Пустой результат может показать временное объяснение в общей панели, но не создаёт краевую карточку или архив.

### Продолжить или явно начать заново

**Continue:** текущие основания действительны, пользователь продолжает обсуждение. Preview включает все основания, все активные предложения этого дела, включая закрытые, и весь текущий диалог. Для ответа добавляется новая атрибутированная пара. Подготовка не пишет SQLite/ledger и не вызывает модель.

**Начать заново и показать предложения:** новая выборка или устаревшая область. Preview содержит только текущие явно выбранные основания, без прежних карточек и пар. Рядом ясно сказано: «Успешный ответ заменит прежнее обсуждение. Предложения будут показаны заново». Один финальный Send подтверждает этот точный запрос и замену. Само изменение выборки такого подтверждения не даёт.

Нельзя незаметно объединять новую выборку с исключёнными прежними основаниями. При обычном изменении дела существующая область становится stale; она не используется для Continue. Пользователь может явно начать заново по текущим данным. Это не автоматический сброс закрытия.

Новая область получает новые ProposalId. Старый набор заменяется целиком, поэтому одновременных копий старого и нового действия нет. Идентичность обычных обновлений не сужается произвольно: в Continue прежние IDs сохраняются. Явный повторный показ не сбрасывает будущую task-level историю напоминаний09.

### Полный набор одного ответа

Provider получает строгий JSON-контракт: `proposals` — полный массив от0 до16 элементов; `rationale` — краткое объяснение результата, в том числе пустого. Поля каждого элемента: `proposal_id` (null либо ID из входного набора), `kind` (`suggestion`/`clarification`), `message`, `rationale`, `evidence_ids`, `step_id`. Лишние поля, ошибочные типы, повторные или чужие IDs отклоняются. Silence представлен пустым массивом, не карточкой с пустым действием.

Continue передаёт все прежние IDs. Повтор прежнего действия должен возвращать его ID, новое действие — null; отсутствующий старый ID удаляется. NewContext не передаёт прежние IDs и принимает только null. Core создаёт IDs новым действиям и проверяет принадлежность, уникальность, все citations, готовность StepId и прежние правила неполного плана. Проверка не превращает текст модели в разрешение запускать агента или менять источник.

Хеш message, StepId и набор citations не определяют смысловое равенство действий. Правильное соответствие прежнему ID — задача модели; этот пакет не вводит вторую модель дедупликации или запрос на каждую карточку. Локальные проверки доказывают применение IDs и границ, но не качество смыслового сопоставления. Последнее требует отдельно отмеченных новых ситуаций с настоящим High Fast.

Стабильный порядок ленты — по ProposalId; новые добавляются после существующих. Перестановка массива ответа не переставляет прежние карточки. Другие дела не входят в текущий модельный запрос и не изменяются его ответом.

### Пределы и атомарность

Не более16 предложений на дело и128 активных предложений всего, включая закрытые и stale. Не более32 пар на область. Сохраняются пределы message16KiB, rationale8KiB,32 citations на предложение, вопрос16KiB/ответ16KiB, model JSON32KiB, context256KiB, HTTP body320KiB. Максимум32 выбранных сведений,64 шага,8 checks на шаг,512 dependencies и32 useful references наследуется от06F.

Все переменные сохраняемые строки и сериализованные ссылки входят в прежний общий лимит64MiB, а не в отдельную квоту. Никакого усечения основания, диалога или полного набора. До POST проверяются доступные входные пределы; после ответа перед публикацией проверяются output/count/global bounds. Результат, не помещающийся в глобальный предел, целиком отклоняется с сохранением прежней области и фактического расхода попытки. Пользователь может завершить дело или явно очистить его предложения с обсуждением; скрытие не освобождает место.

Новые поля входят и в подсчёт retained bytes при записи, и в проверку БД при открытии. Лимиты сериализованной проекции включают весь framing, имена полей и метаданные, а не только пользовательские строки.

Нативная проекция ленты ограничена128 строками и4MiB, строка32KiB; контекст/полные тексты citations не размножаются в каждой карточке. Подробности одного выбранного предложения читаются отдельно с прежним контекстным пределом256KiB. Нельзя выдавать частичный список за все предложения.

До публикации Core проверяет точное сериализованное представление итоговой полной ленты с метаданными:128 строк/4MiB и32KiB на строку. Подробности каждого публикуемого предложения вместе с развёрнутыми citations также должны помещаться в256KiB. Допустимый preview и ответ модели сами по себе этого не гарантируют. При превышении вся публикация отклоняется, прежняя область сохраняется, фактический расход учитывается. Скрытого усечения или дополнительного native-кэша для обхода этих границ нет.

Send использует прежний одноразовый dispatch, durable possible-send и бюджетный журнал. Проверяются exact preview, его режим, TaskVersion/workspace revision, предложение-адресат, все fences, текущие session/report/High Fast и отсутствие паузы. Отмена или timeout не доказывают прекращение запроса; slot освобождается после настоящего cleanup.

Учёт terminal/unknown выполняется прежним владельцем и не откатывается из-за ошибки сохранения ленты. Только проверенный успешный ответ затем в одной SQLite Immediate transaction повторно сверяет все основания и ожидаемые версии, обновляет весь набор/контекст/пары и повышает workspace revision. При любой ошибке эта транзакция не применяет ни одного частичного изменения. Сбой между учётом и публикацией оставляет прежнюю область, известный расход и не запускает retry.

Закрытие во время запроса не отменяет анализ: visibility не повышает workspace revision. В момент публикации совпавший ID наследует **текущую** visibility из той же транзакции, а не копию из preview. Новые IDs видимы. Удаление карточки в полном ответе не удаляет пользовательский черновик.

### Restart, stale, забывание и пауза

При restart Core проверяет схему, пределы и ссылки постоянных данных. Нет автоматического POST. Для copy/Continue нужен новый текущий допуск; старый receipt не восстанавливается. Copy заново проверяет ProposalId/content revision, TaskVersion, все fences, session/report/High Fast и паузу, затем отдаёт точный сохранённый message без модельного запроса. Reply создаёт новый preview через тот же transport.

Обычное изменение текста/плана/сведений повышает TaskVersion и делает область stale. Native показывает это как прежнюю помощь с устаревшими основаниями; copy/ответ отключены. Stale-карточка не утверждает текущее внешнее состояние. Обновление требует явного нового контекста.

Для stale-области подробности не подставляют текущий текст основания вместо прежнего: показываются сохранённое предложение и состояние «основания изменились», а развёрнутые citations недоступны до нового обсуждения. Старые тексты не восстанавливаются из внешнего источника.

Забывание/удаление выбранного Evidence, удаление или завершение дела, отзыв/удаление/исключение source setting немедленно удаляют всю зависимую область, пары и предложения в той же транзакции. Также отменяются производные process previews/requests/results. Зависимость включает непрoцитированные основания. После очистки недопустим откат к прежним производным. Удаление карточек и явная очистка помощи не удаляют исходную пользовательскую память и прежние source tombstones.

Любая смена ревизии использованного source setting также очищает зависимую область: прежний допуск источника больше не действует. Изменение самого сохранённого факта без изменения допуска следует обычному правилу TaskVersion/stale.

Пауза и session loss снимают процессный допуск и останавливают работу по прежним правилам; постоянная область остаётся. Во время паузы полезная краевая лента не активна, доступны только состояние и управление. Resume может восстановить прежние действительные видимые карточки после проверок, но не открывает скрытые и не вызывает модель. В общей панели сохранённые карточки читаются с обозначением недоступности; разрешение copy/ответа не подразумевается.

«Не актуально» через общий Core выставляет `initiative_suppressed` точному делу, скрывает его предложения и инвалидирует процессный допуск. Область остаётся stale; снятие подавления само не открывает её. Ручная новая помощь после явного изменения флага использует NewContext. Флаг и жизненный цикл не дублируются в native.

Закрытие, показ, copy, публикация, перефразирование и новый workspace не считаются продолжением работы или полезным новым фактом. Таймеры09 в этот пакет не входят.

### Минимальная граница Model ABI4

Операции используют прежний memory handle и Store; отдельной БД или registry карточек нет.

- **Feed read:** одна согласованная ограниченная проекция всех активных предложений, их видимости, content/workspace revisions и состояния актуальности. Чтение сохранённых данных для общей панели не требует High и разрешено при паузе; оно не занимает модельный transport и не создаёт допуск к действию.
- **Details read:** точный ProposalId/content revision, предложение и развёрнутые citations только при действительных основаниях; иначе явное stale-состояние без подстановки нового текста. Применяются точные byte limits.
- **Hide / show:** устойчивое закрытие точного ProposalId без изменения смысловых ревизий. Явный show проверяет актуальность и текущий рабочий допуск; hide доступен как локальное управление. Модель не задаёт visibility.
- **Clear discussion:** точное дело с текущими TaskVersion/workspace revision; удаляет только производную область и повышает её revision. Не требует модели/High, доступно из управления памятью.
- **Prepare:** явно выбранный Continue или NewContext. Continue получает ожидаемые версии; optional reply содержит ProposalId/content revision и текст. Reply разрешён только clarification, как в08A. NewContext содержит точную выборку, ожидаемую workspace revision, даже если область сейчас отсутствует, и явное намерение заменить/показать заново. Preview возвращает точные bytes и описанный режим без постоянной записи.
- **Dispatch/result/cancel:** прежний одноразовый lifecycle запроса и ledger с новым контрактом полного набора. Никаких вторых очередей или старых v3 result getter.
- **Copy:** точный ProposalId/content revision, новый текущий допуск и все fences; возвращает проверенный message. Нельзя копировать старую native строку вместо результата Core.

«Не актуально» остаётся общим изменением initiative_suppressed точного дела; дублирующего флага в Model ABI нет. Поздние ответы любого read/prepare проверяются native поколением и не перезаписывают новую ленту/черновик.

### Общая краевая лента, панель и голос

Используется прежний nonactivating NSPanel, bounds/visibleFrame и правила экранов08A. В нём все видимые предложения всех дел, локальная прокрутка и раскрытие деталей. Общая панель использует тот же набор, включая скрытые/stale с понятными состояниями. Скрытые можно явно показать снова без модели, если текущие основания/допуск действительны. Кнопка очистки обсуждения действует на точное дело и убирает только производную помощь.

Один shared draft хранит текст, ProposalId/content revision и своё поколение. Непустой черновик не переадресуется при выборе другой карточки. Пользователь явно решает сохранить текущий ввод или заменить его; автоматической отправки и постоянного autosave черновика нет. При смене содержимого адресата draft остаётся с прежним текстом и stale-состоянием.

При редактировании карточка/редактор и scroll anchor удерживаются; новые карточки добавляются без фокуса и автоскролла. Если адресат исчез, остаётся редактор с пользовательским текстом и сообщением о недоступности, а не копия удалённого вопроса или основания. Перемещение на другой экран выполняется только для сохранения доступности по08A.

Для bounded списка достаточно штатных ScrollView/LazyVStack/ForEach со стабильным ProposalId и macOS14 `scrollPosition(id:anchor:)`; content revision не входит в SwiftUI row identity. Позиция прокрутки принадлежит конкретному окну, текст/адресат — общему draft. Единственный редактор не пересоздаётся при обновлении строки. ScrollViewReader служит явному переходу, а не автоскроллу при фоновом обновлении. Librarian подтвердил API в установленном SDK; фактическое удержание фокуса/положения остаётся отдельной UI-проверкой.

Голос10A использует тот же draft и его поколение: record → check/cancel → локальное распознавание → редактирование → preview → Send. Новая карточка или поздний результат ASR не переносит текст на другой ProposalId. Все правила удаления WAV, удержания helper до выхода и отсутствия streaming-транскрипции сохраняются.

EN/RU меняются вместе. UI объясняет сохранение текущего обсуждения и его очистку; ABI/revision/технические названия не входят в пользовательские тексты.

## Testing Decisions

Реальный путь: временный SQLite → C ABI → Swift shared model → локальный HTTP/SSE → несколько предложений → закрыть одно → Continue с перефразированием и новым действием → restart Store/native → новые допуски → copy/ответ. Модельный ответ подменяется только тестовым сервером.

Обязательные случаи:

- Два действия с одинаковыми citations/StepId не сливаются; прежний ID обновляется, чужой/повторный отклоняется; порядок ответа не переставляет карточки.
- Пустой набор удаляет обсуждение; revision не сбрасывается; старый preview после очистки/пересоздания не публикуется; ID не переиспользуются.
- Restart сохраняет закрытие/диалог/идентичность, но не capability/receipt. Сохранённые reply IDs уникальны и атрибутированы после нескольких restart.
- Close во время POST сохраняется при успешном обновлении. Content revision инвалидирует draft, visibility — нет.
- Preview не пишет DB/ledger/HTTP; Send один; HTTP bytes совпадают с preview. Неудачный NewContext сохраняет старый набор/видимость/текст, успешный заменяет целиком.
- Ordinary edit → stale; delete/forget/revoke, в том числе непрoцитированного Git/Codex основания, → очистка всей области. Отзыв между preview/dispatch/result/copy и поздний ответ не возвращают производные.
- Исторический вопрос остаётся частью разрешённого текущего диалога после снятия его карточки, но не переживает очистку зависимой области.
- Все count/byte limits до/после dispatch; глобальный предел без частичной публикации. Ledger known/unknown не откатывается после SQLite ошибки; автоматического retry нет.
- Основания около240KiB плюс допустимые message16KiB/rationale8KiB: preview и model JSON проходят, но развёрнутые details превышают256KiB; публикация целиком отклоняется с сохранением прежнего workspace и учтённого расхода.
- Независимость дел, точное подавление, пауза/resume/epoch, общий draft, сохранение пользователя при исчезнувшем адресате; голосовой target/generation после обновления ленты.
- Schema7 отвергается без модификации; в Mach-O нет model v3 и test hooks. Git/Codex/голос/план/источники не регрессируют.

До типов — Type Scaffolder read-only; все тексты — Localization Mechanic; готовая логика — Code Simplicity Review. Важный код и типы пишет Sol. Обязательны yarn verify, feature Swift, all-features Clippy, app build/signatures и сохранность checkpoints; доказательства в `target/verification/08b/`, не только `/tmp`.

Фактические UI/focus/scroll/Spaces/multiscreen, микрофон/TCC, macOS14 hardware, Windows, настоящий Fast и качество semantic ID отдельно непроверены. Во время локальной реализации запуск пользовательского приложения, чтение личной памяти и новые cloud/Jev вызовы не нужны. Полная08 не закрывается по unit/HTTP тестам.
