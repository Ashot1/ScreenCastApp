# ADR-004: несколько дел и договор источников памяти

Статус: конкретный независимый срез 07 по D56, проверен Plan Simplicity Reviewer и Evidence Auditor 2026-10-19; блокеры исправлены. Это развитие согласованной памяти, без изменения продуктовых требований. Реализован и принят 2026-10-19: полный `yarn verify` (8 tooling, 17 Rust, 8 Swift), сборка `.app` и проверка подписи прошли. Визуальный UI-прогон и Windows не проверялись; полная 07 остаётся открытой.

## Граница среза

Один владелец расширяет настоящий путь Swift → C → Rust/SQLite: создать несколько дел, выбрать/прочитать/изменить дело, добавить ручную заметку, исправить её привязку и удалить дело/заметку. Ручная заметка имеет происхождение «пользователь», не изображает чтение внешнего сервиса. Пользователь может явно связать два дела и убрать неверную связь. Память и настройки доступны при остановленном помощнике; наблюдение, голос, автоматические связи и инициатива остаются остановлены.

Общий источник памяти принимает настоящие типизированные сведения, но подключения сервисов в этом срезе нет. Его поведение проверяется синтетическими входами в тестах реального хранилища; production-подделок нет. План/зависимости/следующий шаг, завершение с кратким итогом, автоматические уточнения и модельная полезность остаются открытыми критериями 07. Ни один из них не подменяется полем-заглушкой.

## Владение, идентичность и исправление

Rust владеет делами, сведениями, привязками, ревизиями и удалением. Swift хранит подтверждённый снимок для отображения, выбранный ID и один самостоятельный черновик с исходными ID/ревизией. Перед сменой дела с изменённым черновиком доступны сохранить, отбросить или отменить переключение. Ошибка сохранения не стирает черновик; пустой черновик и точные UTF-8 байты сохраняют нынешнюю семантику. Пауза остаётся глобальной и независимой от дела.

Локальные ID — непрозрачные положительные SQLite `INTEGER PRIMARY KEY`. Строка идентичности дела/сведения остаётся после удаления, поэтому ID не переиспользуется. Сравнение/генерация ID принадлежат Rust, они не обозначают окно, URL или позицию списка. Нельзя удалять строку идентичности или самостоятельно уменьшать счётчик ради освобождения места. Ревизии положительные, ограничены `i64::MAX`, меняются атомарно; превышение явно отклоняется.

Операция изменения принимает ожидаемую ревизию. Изменение содержания, связи или привязки сведений атомарно повышает ревизии затронутых дел; поздняя операция со старой ревизией отвергается. Явная перепривязка записывает пользовательское подтверждение/отклонение прежней привязки. Поздние предположения источника не отменяют пользовательское решение. Связь дел в этом срезе — явная симметричная связь «связаны», без workflow engine. Решение «не связывать» хранится как пользовательское решение, пока соответствующие дела не удалены.

Сведение содержит текст утверждения, ID дела/сведения, происхождение, время наблюдения UTC и полноту `complete / partial / unknown`; различаются факт источника, предположение и подтверждение пользователя. Происхождение — пользователь без выдуманного внешнего ключа либо внешний объект с ключом и необязательной версией. Для ручного утверждения записывается время действия пользователя; неизвестное внешнее время не заменяется текущим. Внешний ключ обозначает основание, а пользовательское исправление явно отмечается подтверждением пользователя. Неизвестная полнота или недоступный источник не становятся отрицательным фактом. Точный промпт или ссылка остаются текстом источника, не выдумываются и не превращаются автоматически в действие.

Подтверждение привязки объекта к делу не является подтверждением всего его содержания: последующие факты этого источника могут обновляться при соблюдении ревизии. Отдельное пользовательское исправление самого утверждения защищено от перезаписи историческим импортом. Эти решения различаются и не сводятся к одному общему флагу «подтверждено».

Отдельная ревизия каждой заметки/привязки пока не нужна: все операции проверяют и повышают ревизии всех затронутых дел, а удалённый ID остаётся терминальным. Внешняя версия объекта не заменяет эту проверку и не сравнивается лексикографически как время. Историческое поступление всегда адресует существующее дело с ожидаемой ревизией и никогда не создаёт дело само. Асинхронный импорт ещё не привязанного объекта потребует собственного проверенного допуска в будущем, не маскируется этим контрактом.

## Ключ источника и забывание

Ключ внешнего объекта — точный кортеж `(adapter namespace, account/install scope, object ID)`, предоставленный адаптером. Это не заголовок, текст, foreground window или неявно нормализованная URL. Версия объекта необязательна и хранится отдельно от идентичности. Все три компонента — непустые UTF-8 без NUL; если версия присутствует, она также непустая и без NUL. Значения не содержат секретов; сравнение точное, без trim/case-folding. Поддержка конкретных алиасов проверяется с соответствующим адаптером, а не угадывается в памяти.

Единица импорта — одна запись на пару `(дело, ключ объекта)`, обновляемая с сохранением ID. Один объект не порождает неограниченные заново назначаемые ID утверждений. Ручные заметки — отдельные записи. Если будущему адаптеру нужны независимые части объекта, он должен предоставить их устойчивые идентичности в своём проверенном контракте, а не генерировать новый ID на каждом чтении.

Для отметки забывания Rust рассчитывает SHA-256 ключа: фиксированная версия кодирования и три точных UTF-8 поля, перед каждым длина `u32` в big-endian. Не хешируем текст дела/заметки или версию объекта. Используем проверенную библиотеку `sha2 = 0.11.1`, без ненужных features; новый самописный хеш или ключ/его жизненный цикл не вводятся. Хеш не является шифрованием: угадываемый идентификатор можно перебрать. Это минимальная отметка сопоставления, а не обещание скрыть ID от владельца БД.

Удаление одной транзакцией очищает содержание дела/сведений и принадлежащие им производные/связи. Остаются ID, ревизия удаления и отпечатки уже известных ключей. Служебная отметка не содержит текста, заголовка или исходного ключа. Поздняя операция с удалённым ID всегда отклоняется. Повтор исторического источника с известным забытым ключом не создаёт новую неявную привязку; контракт возвращает явный исход `forgotten`. Удаление импортированной записи блокирует исторический повтор этой пары даже с новой версией объекта или предлагаемым новым ID. При этом существующая подтверждённая привязка того же объекта к другому живому делу остаётся читаемой и обновляемой; её независимые сведения не стираются.

Явное новое действие пользователя может связать объект заново с новым живым делом, но не оживляет старый ID и не возвращает старое содержание/производные. Историческое поступление и явная пользовательская привязка — разные операции. Core не считает текст источника таким разрешением. Пока нет реальных подключений, доказана только защита по известным точным ключам; узнавание неизвестных алиасов/того же содержания в другом источнике не заявляется.

Место под фиксированную отметку резервируется при создании идентичности/первой привязке: один слот на дело/заметку и один слот 32-байтового отпечатка на привязку источника. Удаление переводит уже выделенные записи в состояние удаления, а не требует свободных новых слотов. Слоты, живые строки и отметки вместе учитываются в лимитах соответствующего вида. Лимит нового накопления не должен запрещать удаление; отметки нельзя молча вытеснять. Удаление отдельной заметки сохраняет её ID и при необходимости отпечаток, чтобы поздний ответ не вернул её текст.

## Ограничения и нативная граница

Лимиты относятся к этому первому контракту и проверяются до записи: каждое намерение/утверждение/заметка — 16 384 UTF-8 байта; namespace — 64, scope — 256, object ID — 2 048, необязательная версия — 256 UTF-8 байт. Не обрезать содержание. В сообщениях ошибок нет исходного текста/ключей. Одновременно живых дел не более 1 024; всего строк идентичности дел, включая удалённые, — 100 000; сведений/привязок/решений — не более 100 000 каждого вида, включая отметки и резервные слоты. Общий сохраняемый текст и исходные ключи ограничены 64 MiB; фиксированные метаданные отдельно ограничены числом строк. Это не обещание такого же физического размера SQLite. Достигнутый предел даёт видимую ошибку и сохраняет старое состояние; подтверждённые ошибки не маскируются пустым списком.

Списки дел, заметок, источников и связей выдаются страницами до 50 элементов и 256 KiB полезных данных; неограниченных вложенных коллекций в одном элементе нет. Если по байтам помещается меньше, возвращается корректная меньшая страница с продолжением. Один допустимый элемент всегда помещается. Пагинация опирается на стабильный ID, а не позицию UI; после мутации UI перечитывает нужную страницу. Контракт не требует неограниченного полного снимка всей памяти.

Сохраняются синхронные вызовы вне UI actor, caller-owned буферы, явные lengths/error codes и закрытие после принятых операций. Нет callbacks, второго хранилища, подписок на собственную память, универсальной шины или скрытого JSON-протокола. Read-only Type Scaffolder сверяет конкретные Rust/C/Swift типы до зависимого кода; важный код пишет Sol.

## Схема и ошибки

Новая схема 2 заменяет однонамеренную схему в исходниках и использует прежний путь БД. Включаются и проверяются SQLite foreign keys; связанные изменения выполняются одной `Immediate` транзакцией, ограничения и параметры SQL остаются нативными. Устаревшие singleton API/типы/тесты удаляются по мере замены рабочим путём, совместимый дубль не сохраняется.

Существующая БД схемы 1 или чужая/повреждённая БД сохраняется без изменения и даёт явную ошибку неподдерживаемой схемы. Автоматической миграции, сброса, скрытой смены файла или чтения пользовательской БД ради проверки нет. Мы не предполагаем, что её нет, лишь потому что агент не запускал приложение. Инициализация допускается только для новой пустой БД. `secure_delete=ON`, `journal_mode=DELETE`, отсутствие шифрования/обещания физического стирания сохраняются из ADR-003.

Перед началом 07 проверено только существование известного пути: ни каталог `Application Support/dev.ambient.foundation`, ни `memory.sqlite3` на этом Mac не существуют. Содержимое пользовательских файлов не читалось. Проверенная сборка 06 сохранена в `target/checkpoints/Ambient-foundation-06.app`, подпись повторно проверена; её нельзя перезаписывать следующей сборкой. Если пользователь успеет создать схему 1 старой сборкой, эта сохранённая сборка остаётся способом открыть/прочитать/скопировать его намерение. Новая сборка сообщает несовместимую схему и не удаляет её. Это локальный артефакт предыдущего среза, не production-слой совместимости или скрытый перенос данных. Переход реальных пользовательских данных между версиями остаётся отдельным явным действием; автономно его не выполняем.

## Приёмка

Настоящие SQLite/ABI/Swift tests: несколько дел и выбор, точное редактирование, черновик при смене/ошибке, заметка и перепривязка, подтверждение против поздней ревизии, перезапуск, ошибки/лимиты страниц и суммарных байтов, атомарный rollback, удаление и повтор известной истории, другой живой пользователь той же связи, явная новая привязка без восстановления старого текста. Отдельно: удаление импортированной записи → та же история с новой версией/предлагаемым ID → `forgotten`, при этом другое дело с существующей привязкой обновляется. Схема 1 остаётся побайтово сохранной при отказе открытия до DDL/меняющих pragmas. Все прежние применимые границы паузы/UTF-8/закрытия также проверяются.

Нужны полный `yarn verify`, сборка `.app`, Code Simplicity Review и обновление затронутой документации. Визуальный UI-прогон не запрошен. Проверенная часть открывает только потребителей фактически готового договора памяти/источников; полный билет 07 и G6 остаются открытыми.
