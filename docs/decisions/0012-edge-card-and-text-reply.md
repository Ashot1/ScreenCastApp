# ADR-012: краевая карточка и текстовый ответ

Статус: 08A реализован и принят локально 19 октября 2026. Verify 8 tooling / 105 Rust / 51 Swift, feature Swift 72, build/signatures/review PASS; контрольная сборка Ambient-reply-08a.app. Фактические UI/focus/Spaces и полные07/08/09/10 остаются открытыми.

## Problem Statement

Результат06F виден только внутри окна памяти. Чтобы ответить на уточнение, приходится самому сохранять заметку и запускать помощь заново. Нужен ответ рядом с карточкой, без перехвата фокуса и подмены адресата. Это также определяет текстовый путь будущего голосового ответа10.

## Solution

Один текущий результат существующего ручного запроса показывается у края экрана и в общей панели. Там доступны основание, копирование, скрытие и «Не актуально». На уточнение можно ответить текстом, в том числе вставить «Да» или «Нет». Локально подготовленный точный preview доступен рядом с редактором. Единственное финальное «Отправить» передаёт его прежним High Fast транспортом.

Вопрос и ответ остаются временным контекстом текущего взаимодействия. Они не становятся автоматически ручной заметкой или подтверждённым фактом. Сохранение необходимого нового рабочего контекста, намерений и обязательств остаётся частью полной07; этот пакет не объявляет её выполненной. Существующие явные изменения памяти и связей сохраняют своё действие.

## User Stories

1. Я вижу готовую помощь у края экрана, не возвращаясь обязательно в основное окно.
2. Появление карточки не отнимает клавиатуру у приложения, в котором я работаю.
3. Я раскрываю основание и читаю длинный текст в самой карточке.
4. Я копирую только актуальный текст по явному нажатию.
5. Я отвечаю на уточнение там же, где оно появилось; «да» не теряет исходный вопрос.
6. Я могу проверить точный состав отправки и подтверждаю её одной кнопкой.
7. Редактирование текста не вызывает модель и не создаёт сохранённый факт.
8. Новый результат, смена дела, пауза или ошибка не затирают мой неотправленный текст и не меняют его адресата.
9. Удалённые или исключённые сведения не возвращаются через процитировавший их вопрос.
10. Закрытие скрывает карточку сейчас; «Не актуально» меняет общий флаг дела, а не внешний источник.
11. Я могу открыть ту же карточку в общей панели; второго черновика и двух расходящихся результатов нет.
12. Я вижу честное сообщение об устаревшем адресате, недоступности или достигнутом пределе, без скрытого повторного запроса.

## Implementation Decisions

### Владение и граница пакета

Core сохраняет одного владельца результата, снимка, допуска и журнала. Native владеет одним самостоятельным черновиком ответа и окном. Используются прежние coordinator, транспорт и долговечный учёт попыток. Никаких нового чата, постоянного transcript, второго хранилища, планировщика или production mock.

В пакете остаётся один текущий результат ADR-010. Это не замена полной ленты08: несколько разных действий и их обновление остаются обязательными последующими критериями. Ответ добавляется к результату-уточнению; предложение имеет copy, silence остаётся сообщением в общей панели и не создаёт краевое предложение.

После принятой11A сохраняются schema6, memory ABI3, auth ABI1 и local-source ABI1. Model ABI3 заменяет2 целиком, поскольку добавляется контракт follow-up; старые экспорты удаляются. Общий формат ответа модели, модель/effort/tier и предел журнала не меняются. Согласованные версии implementer сверяет после окончания11A.

### Временный ответ и один preview

Native передаёт текущий parent receipt и текст ответа, а не текст вопроса и не произвольный prompt. Core проверяет текущий действительный clarification, сам берёт вопрос и строит один заменяемый pending preview. Родительский результат при подготовке не теряется. Подготовка не пишет SQLite/ledger, не создаёт model operation и не отправляет HTTP.

Follow-up наследует **весь** исходный снимок: дело и ревизию, выбранные сведения, план, проверки, ссылки, ревизии настроек источников и session epoch. Только процитированных моделью evidence IDs недостаточно: вопрос мог использовать любое отправленное основание. Внутри контекста отдельны текст модели и точный пользовательский ввод. Ответ пользователя не означает автоматического подтверждения предпосылки вопроса.

У временного ответа может быть citation вида `reply:<request-id>` с отдельным типом Reply; это не EvidenceId и не сохранённый факт. Его отображение явно различает вопрос модели и ответ пользователя. Обычные citations и валидация ссылок сохраняются; модель не получает разрешение на действие из ответа.

Пределы:16KiB на пользовательский ответ и прежний предел16KiB на вопрос; максимум32 подтверждённые пары текущего диалога; общий context256KiB/body320KiB. Изменения одного черновика не считаются новыми ходами. Переполнение отклоняется до POST с понятным сообщением; нельзя молча обрезать ранние ответы, выбранные сведения или план. После ошибки можно сохранить важное явными существующими операциями памяти и начать новый ручной запрос.

Одновременно существуют только текущий снимок/результат и один pending preview. Все их строки ограничены указанными байтовыми пределами. Подготовки черновика не накапливаются в очереди: native держит одну выполняемую и самое новое значение либо использует штатную отмену задачи с проверкой её поколения. Поздний preview не заменяет preview нового текста. Отправка доступна лишь для точного совпадения версии черновика и подготовленного preview. Детали можно раскрыть без отдельного подтверждения и без записи данных.

### Единственное подтверждение и отмена

Кнопка «Отправить» потребляет текущий pending preview ровно один раз. Core повторно проверяет parent receipt, всю актуальность контекста, current session/report/High Fast, отсутствие паузы и занятого transport. Затем заменяет текущий снимок подготовленным follow-up и использует прежние begin/dispatch/ledger/finish. Ревизия дела не меняется, в памяти нет новой записи. В транспорт идут именно показанные bytes, а не заново собранный контекст.

Существующая durable possible-send запись выполняется до POST; unknown не обнуляется. Отмена и таймаут не доказывают прекращение удалённой генерации; занятость освобождается после настоящего cleanup. Нет повторной отправки, другой модели, default вместо Fast или автоматического запроса после восстановления.

Подтверждённо отправленный текст не остаётся новым неотправленным черновиком после успешного результата. При ошибке пользовательский текст сохраняется, но старый receipt не становится разрешением повторить попытку. Если нужен новый адресат, его выбирают явно; старый текст не прикрепляется автоматически. Состояние отправки и ошибки видно в обеих поверхностях.

Пауза, logout/смена epoch, отзыв допуска, изменение/удаление дела, плана, свидетельств или используемых root settings инвалидируют parent, pending и производный результат по тем же правилам06F/11A. Проверки действуют до prepare/dispatch/result/copy. Сгенерированные вопрос и context освобождаются, поздний ответ не возвращает их. Самостоятельный введённый пользователем текст остаётся отключённым от отправки черновиком; он не превращается в независимую manual note. При закрытии приложения неподтверждённый временный диалог не сохраняется; долговременный редактор/автосохранение черновиков этим пакетом не вводятся.

### Нативная карточка

Используется один AppKit NSPanel с nonactivatingPanel и SwiftUI содержимым. Показ через orderFrontRegardless не делает приложение активным. Floating level и системные collectionBehavior используются без глобального перехвата клавиатуры/мыши. Фокус редактора даётся только при явном взаимодействии; панель не должна перехватывать клики за пределами своего окна.

При первом показе выбирается экран точки текущего указателя через NSScreen.screens/NSEvent.mouseLocation; координаты — points, область размещения — visibleFrame. Выбор не выдаётся за знание активного приложения. Карточка располагается у правого края, имеет ограниченные размеры, перенос строк и локальную прокрутку. При взаимодействии позиция и адресат фиксированы. Смена экрана, его исчезновение или изменение usable frame корректируют геометрию только чтобы карточка оставалась доступной; новый результат сам по себе не двигает редактируемую карточку.

Общая панель и краевое окно используют один UI owner черновика/раскрытия/результата. Переключение выбранного дела в памяти не переносит ответ. Если новый результат приходит при непустом неподтверждённом черновике, старый редактор сохраняет текст и явно показывает неактуальность; новый результат доступен через явный переход после решения о старом черновике. Не вводить бесконечный backlog: только один текущий результат и один самостоятельный черновик.

«Закрыть» скрывает текущую краевую карточку; повторный render того же receipt её не открывает. Общая панель позволяет явно показать её снова. Это UI-видимость, не выполненный цикл09. «Не актуально» через общий Core применяет initiative_suppressed=true к точному делу/ревизии, инвалидирует результат и не меняет внешний статус. UI не превращает операцию в toggle чужого выбранного дела. Само наличие флага не доказывает готовые напоминания09.

Пауза и недоступность видны без создания нового полезного предложения. EN/RU обновляются вместе. В настройках/помощи кратко обозначена временность диалога; технические ABI/epochs не попадают в пользовательский поток.

## Testing Decisions

Использовать существующие реальные Store/SQLite, C bridge, native модели и локальный HTTP/SSE сервер. Сквозной путь: исходный ручной запрос → clarification → общий черновик → exact preview без DB/HTTP → единственное Send → второй ответ → разрешённое copy. Дополнительный ход подтверждает сохранность временного контекста. Модельная подмена допустима только внутри тестового HTTP сервера.

Проверить: preview byte equality; последняя версия черновика; один dispatch; отсутствие записей памяти/новой схемы; отдельную атрибуцию reply citation; размер/count до POST; stale parent; смену выбранного дела; паузу/ошибку/поздний ответ с сохранением только пользовательского текста; источники, не упомянутые в citations, но присутствующие в контексте; root exclusion/delete после preview и до copy; удаление основания и невозможность вернуть его вопросом; отсутствие скрытых повторов; одноразовое скрытие и точную suppression цели; shared UI draft без второго редактора памяти.

До типов — Type Scaffolder read-only; новые тексты — Localization Mechanic; готовая логика — Code Simplicity Review. Важный код и типы пишет Sol. Обязательны полный yarn verify, app build/signature, отсутствие test-only экспорта во всех Mach-O и сохранность предыдущих checkpoints. Native UI, ввод/фокус, Spaces, несколько экранов/масштабы, macOS14 hardware, Windows и live High Fast не считаются проверенными по unit/HTTP тестам. UI-прогон сейчас не запрошен; никаких TCC, регистрации автозапуска или запуска пользовательских приложений во время пакета.
