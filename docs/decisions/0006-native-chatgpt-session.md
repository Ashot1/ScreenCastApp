# ADR-006: собственный нативный вход ChatGPT

Статус: спецификация независимого пакета 06B по D55/D56 принята после Plan Simplicity Review и Evidence Audit, включая целевую проверку исправлений host ID, постоянного адреса Keychain и срока операции. Реализация завершена и принята после локальных проверок: 8 tooling / 46 Rust / 27 Swift tests, app build/codesign PASS. Работа выполнена после приёмки 07B в треде `01a151a5-d623-78d1-874b-6bec23f56510`; владельцы Rust–C–Swift не пересекаются. Этот пакет переносит в приложение реальный вход и сохранение сессии, не ждёт Fast и не подтверждает полную 06.

## Результат и граница

Пользователь нажимает Continue with ChatGPT в настройках Ambient, проходит собственный вход, приложение проверяет личность/права и сохраняет сессию в Keychain. Следующий запуск читает сохранённый вход без браузера. Есть явные отмена, обновление истёкшего подключения и локальный выход. Нативная собственная регистрация отличается от регистрации Node-стенда: ни Codex credentials, ни cache/Keychain-элементы стенда не заимствуются и не мигрируют.

Этот пакет не отправляет Responses, не читает рабочий контекст, не запускает Jev/захват/голос, не проверяет Fast и не делает помощника работающим. «Вход сохранён» и «Анализ доступен» различаются: анализ по-прежнему остановлен. Настройка входа доступна по явному действию при остановке. Автоматических сетевых вызовов на старте/периодического refresh нет; при запуске только локальное чтение своей записи. Дальнейший потребитель сможет запросить готовую сессию через эту же границу после общего runtime admission, не создавая второй менеджер входа.

Первый native consent, пользовательский Keychain ACL и реальный refresh ещё требуют отдельного подтверждения на настоящем аккаунте. Их отсутствие не запрещает реализовать и проверить путь на локальном тестовом IdP и изолированном тестовом Keychain, но такая проверка не называется реальным входом пользователя. Новых model POST для этого пакета нет; $1/$1.50/$2.50 Jev и все прежние unknown usage не затрагиваются.

Приёмка06B подтверждает local HTTP/OIDC, isolated Keychain, сохранение сессии, отмену и app shutdown. Используется file-based Keychain через SecItem с системным ACL и без синхронизации: Data Protection access groups недоступны текущей ad hoc подписи без provisioning entitlements. После пересборки ОС может снова запросить доступ к записи; этот ACL-путь на пользовательском аккаунте ещё не проверен. Контрольная сборка — `target/checkpoints/Ambient-session-06b.app`, подпись проверена координатором.

## Владение и библиотеки

Rust в `src/providers` владеет конкретным SIWC протоколом: OIDC discovery, URL авторизации, PKCE/state/nonce, callback/выданный client ID, обмен/refresh, проверка JWT и выданных scopes. Браузер, локальный HTTP listener, долговременный Keychain и UI — native. Типы SDK не становятся core/domain/C контрактом. Новая скомпилированная provider crate нужна для этого реального пути; core не зависит от native shell. Нет универсального auth framework, provider registry для будущих поставщиков, Node runtime или собственной криптографии.

Принят независимый вариант Plan Simplicity Reviewer: `openidconnect = =4.0.1`, default-features=false; `reqwest = =0.12.28`, default-features=false, features rustls-tls. Для синхронной границы добавлена прямая зависимость `tokio = =1.53.3` с rt/net/time: версия уже закреплена транзитивно, короткий runtime обслуживает только один HTTP-вызов. Исследователь проверил совместимость с oauth2 5/http1 и лицензии MIT / MIT+Apache-2.0; сборка на нашей macOS ещё должна пройти. Прямые serde-типы допустимы только если нужны для дополнительных проверяемых OIDC claims; не создавать собственный JWT parser. Cargo.lock закрепляет фактически разрешённый набор.

AppAuth + JWTKit не используются: AppAuth не проверяет подпись, его initial auto-exchange берёт dynamic client ID вместо выданного, а bundled loopback server не ограничивает входной буфер. macOS предоставляет более узкую композицию: Network.NWListener/NWConnection для TCP, CFNetwork.CFHTTPMessage для штатного HTTP-разбора и Security.framework для Keychain. Дополнительная Swift-библиотека не нужна.

## HTTP поставщика

Сеть выполняется синхронно вне UI на отдельном последовательном auth executor, не под registry mutex памяти и не в MemorySession. Одна активная auth-операция на приложение; таймауты не замораживают управление памятью.

Фиксированные адреса: issuer `https://auth.openai.com`; GET `/.well-known/openid-configuration` и `/.well-known/jwks.json` на нём; browser authorization `/api/accounts/authorize`; единственный token POST `/api/accounts/oauth/token`; resource `https://api.openai.com/v1`. Discovery должен совпасть с issuer/authorize/token/JWKS и объявлять RS256. Credentials не отправляются на discovery/JWKS. Другие сетевые адреса/методы, redirect и скрытые retries запрещены. Browser URL строит Rust из проверенного протокола, а native не принимает произвольный URL от UI/источника.

Использовать bounded `SyncHttpClient` библиотеки: HttpRequest → reqwest → ограниченный HttpResponse. Встроенный oauth2 blocking transport с unbounded read_to_end не подходит. Async response читается чанками внутри runtime до разбора. До добавления каждого чанка проверяется checked сумма длины; переполнение отклоняется без накопления сверх 512 KiB. Достижение ровно лимита само по себе не доказывает EOF: следующий непустой чанк отвергается. Limit 512 KiB для каждого metadata/JWKS/token response. Requests ограничены 64 KiB; число requests одного prepare не больше двух GET, одного exchange/refresh — одного POST, без автоматического повторного запроса при ошибке/unknown kid. В тестах доказать отсутствие POST retry/redirect.

reqwest: redirect Policy::none, retry::never. Внутри синхронного SyncHttpClient::call создаётся current-thread Tokio runtime с I/O/time drivers; block_on охватывает создание async Client, dispatch и полное ограниченное чтение тела. Client/response не переживают runtime и не кешируются между вызовами. ClientBuilder задаёт total timeout min(15s, остаток срока операции), connect timeout 5s, read timeout 5s. Перед dispatch, между чанками и перед возвратом проверяются отмена/срок. Блокирующая reqwest-обёртка и преобразование builder удалены: реальный TDD-тест обнаружил panic при создании read timer вне reactor. Предел15s относится к запросу, не обещает завершение внутренних DNS blocking tasks; обычный Runtime::drop ждёт их, и до возврата всего вызова native сохраняет busy. Не использовать shutdown_timeout/background shutdown/забывание runtime для ложного Finished. Ошибки HTTP/OIDC отображаются в ограниченный enum и стадию, без Display сырых SDK errors, server detail, URL/query, code, keys, tokens или исходного JSON. Текстовые ошибки не сохраняют секреты.

## Нативный callback

До браузера запускается IPv4 listener только `127.0.0.1` с свободным портом, точный URI `http://127.0.0.1:<port>/auth/callback`. Scheme/host/path фиксированы; между входами может меняться порт. Операция хранит точный URI и использует его при code exchange. Не подменять localhost, IPv6 или custom scheme.

NWParameters.requiredLocalEndpoint задаёт IPv4 loopback; listener.newConnectionLimit ограничивает число принятых соединений за попытку восемью, одновременно не более двух. Каждое соединение имеет 5s deadline и общий предел 8 KiB полученных bytes до/включая заголовки; проверять предел до CFHTTPMessageAppendBytes. CFHTTPMessage принадлежит одному сериализованному native-владельцу, не вызывается конкурентно. Использовать системные CreateEmpty/AppendBytes/IsHeaderComplete/CopyRequestMethod/CopyRequestURL/CopyHeaderFieldValue, не свой HTTP parser.

Принимается только GET без тела/Transfer-Encoding, с точным loopback host/портом/путём. Content-Length допустим только отсутствующий или 0; нестандартные absolute/relative request-target и Host header проверяются тестами и отклоняются, если их нельзя однозначно сопоставить с ожидаемым URI. Лишние bytes/body не используются. Rust проверяет полный bounded callback URL, дубли/отсутствующие параметры, state и ожидаемый client ID; callback scope не считается выданными правами. Ошибочный чужой state не потребляет попытку; число входов всё равно ограничено. OAuth error с правильным state завершает попытку без POST. После принятого callback второй не принимается.

Общий срок операции входа — 5 минут по монотонным часам с момента начала; idle verifier/code не живут бесконечно. Истечение срока запрещает последующие dispatch и commit; завершение уже начатого blocking вызова и очистка соединений могут закончиться позднее, и до их фактического окончания операция остаётся занятой. Возвращаемый браузеру текст статический, без отражения query/кода, с no-store и Connection: close. Завершение/ошибка/отмена закрывают listener и все принятые соединения; наблюдать `.cancelled`/terminal состояния, а не считать один вызов cancel подтверждением освобождения. Нативный timer нужен только для этих сроков, не создаёт планировщик дел.

## Первый и повторный вход

Перед первым входом native один раз сохраняет host UUID в формате `urn:uuid:...`; это публичная установочная идентичность, не токен. Каждый authorization URL, как initial, так и returning, содержит обязательный `ext_agent_host_id` с этим же сохранённым UUID. Rust генерирует свежие state/nonce/PKCE S256 библиотекой. Первый browser request использует `dynamic_agent_client` и `agent_name_hint=Ambient`; следующие — сохранённый issued client ID без name hint. Scopes: openid profile email offline_access resource.invoke chatgpt.tokens.use.direct; resource задан и при авторизации, и при exchange. Public client не имеет client secret/API key; AuthType::RequestBody задан явно.

Native сохраняет marker начатой динамической регистрации до открытия браузера. Если браузер не был открыт, marker можно убрать; после открытия без достоверного callback исход регистрации неизвестен, новый dynamic вход автоматически не создаётся. UI предлагает понятное восстановление: пользователь явно подтверждает, что вход не завершал, либо проверяет своё подключение в ChatGPT. Это не повод требовать такого подтверждения при каждом запуске или при наличии issued ID. Marker не считается подтверждённой учётной записью.

После callback Rust сначала проверяет state/error/дубли и извлекает issued ID (1..512 ASCII букв/цифр/_/-, не dynamic_agent_client). Для returning callback отсутствие ID допускается; другой ID отвергается. Rust держит code/verifier в памяти; native сохраняет issued ID как pending до exchange. При отказе сохранения POST не выполняется. Pending issued ID остаётся для повторного входа даже после invalid_grant/сбоя; это ещё не verified identity.

Exchange создаёт библиотечный клиент уже с issued ID. Проверки: JWT подпись через pinned JWKS, только RS256; точные issuer, audience issued ID, expiry без дополнительного clock tolerance, сохранённый nonce, непустой bounded sub. Если `azp` есть, он совпадает с issued ID; при нескольких aud требуется согласованный azp. Не полагаться на отсутствие встроенной проверки azp в библиотеке: читать `claims.authorized_party()` из штатного библиотечного типа, не добавлять собственный claim/parser только ради azp и не декодировать JWT вручную. Если есть at_hash, проверять его библиотекой для возвращённого access token. Для returning bound registration issuer/sub/client ID должны совпасть. Email не является идентичностью и не нужен в этом срезе.

Для готовой сессии нужны token_type Bearer, непустые access/refresh tokens, положительный expires_in с проверенным сложением UTC и token response scopes openid/resource.invoke/chatgpt.tokens.use.direct. Requested scopes не подменяют grant; в первом обмене отсутствие scope не доказывает разрешение. Корректная verified identity без нужного scope/refresh сохраняет bound registration для повторной авторизации, но не активную сессию. ID token сохраняется как Keychain-only hint согласно официальному SIWC; проверенная identity важнее hint. Hint при повторном входе может быть истёкшим, но не является доступом к анализу. Никакие сырые claims/token не попадают в UI state или логи.

## Одно хранилище credentials и refresh

Native владеет одной защищённой generic-password Keychain-записью фиксированного service `dev.ambient.foundation.chatgpt` и фиксированного account `installation`, без синхронизации между устройствами. При каждом старте ищется именно эта запись; UUID не нужен для её нахождения и не дублируется в UserDefaults/файле. Только `errSecItemNotFound` означает отсутствие: при первом явном входе native создаёт UUID, сохраняет начальный envelope до открытия браузера и впредь использует этот же UUID. Остальные ошибки и повреждение не создают новую регистрацию. Это собственная запись приложения, не общая запись Codex или тестового стенда. В ней один bounded Codable envelope: версия, host, registration (none/dynamic-pending/pending-issued/bound), точные issuer/client ID/verified subject при наличии, retained validated ID-token hint и исходный nonce, optional credentials (access/refresh/granted scopes/expires_at). Нет второго файла с токенами или session DB Rust. Формат Codable только для native persistence; через C передаются типизированные поля и spans, не JSON.

Сохранение envelope использует атомарный SecItemAdd/Update; read/validation/storage failure не становится пустым успешным подключением или автоматическим браузерным входом. Не менять search list/default Keychain/ACL ради обхода. UI показывает «Вход сохранён» по проверенной форме/сроку локальной записи, не обещает серверную достижимость. Истёкшая запись не считается действующей.

Refresh сначала готовит/проверяет публичные metadata/JWKS и параметры результата, не удаляя старые credentials. При ошибке prepare старая запись остаётся. Перед единственным token POST native атомарно переписывает тот же envelope без access/refresh, сохраняя регистрацию/hint; неуспех этой операции запрещает отправку. Только после подтверждённого удаления credentials вызывается dispatch. При cancel между удалением и dispatch старый токен не восстанавливается автоматически; требуется повторный вход с тем же ID.

Refresh POST: grant_type refresh_token, issued client ID, текущий refresh token, resource; без scope/client secret/PKCE. Новый replacement refresh token и срок обязательны. Отсутствующий response scope сохраняет прежний grant; присутствующий заменяет и проверяется. Новый ID token необязателен: если есть, проверяются подпись/issuer/audience/expiry/сохранённый sub и nonce, если nonce присутствует; отсутствие nonce допускается. Если ID token отсутствует, остаются прежние verified identity/hint/nonce. Сетевой unknown, потеря ответа, отмена после dispatch, ошибка проверки/хранения не разрешают повтор старого rotating token. Нет автоматического браузерного fallback. Отказ сети не объявляется доказанным отзывом аккаунта.

Весь новый envelope сохраняется атомарно до показа готовой сессии. Локальный выход удаляет credentials/hint/nonce и отменяет текущую попытку, сохраняя issued registration/binding и host для будущего входа; UI объясняет, что это локальный выход, не отзыв подключения на сервере. Выход из неизвестной динамической регистрации не притворяется её сверкой. Реальный отзыв/удаление записи в ChatGPT не выполняется автоматически.

## ABI, отмена и пределы

Отдельная узкая auth ABI v1 и handle/registry, без изменения memory ABI v3 по смыслу. Один native AuthCoordinator владеет своей сессией и сериализует Keychain commit/logout. Rust владеет только текущим протоколом операции. Вызовы prepare-sign-in, accept-callback, exchange, prepare-refresh, dispatch-refresh имеют проверенную одноразовую последовательность. UI status — проекция результата/локального envelope, не второй сохранённый ledger в core.

Sync вызовы принимаются на отдельном auth executor вне MainActor и MemorySession; глобальный lock registry освобождается до сетевого I/O. Нет callbacks, универсальной HTTP-очереди через ABI и бессрочного фонового runtime. Cancel — короткий потокобезопасный запрос, который не ждёт занятого сетевого lock; native одновременно блокирует поздний commit по поколению операции. CancelRequested отличается от фактического Finished/Cancelled. Операция остаётся занятой до завершения уже начатого blocking вызова/соединений; close ждёт принятый вызов на native стороне и не освобождает занятые данные. Повторный handle не переиспользуется. Logout и late-success не могут сохранить токены после выхода.

Caller-owned фиксированные записи и bytes; SDK типы, указатели на Swift объекты и исключения не пересекают ABI. Для одноразового network call все output capacities проверены до dispatch; минимальная вместимость максимального результата известна заранее. BUFFER_TOO_SMALL не заставляет повторить POST. После actual POST никакой ошибки не трактовать как «не отправлено» без доказательства. Secrets transient только в своих buffers/операции, не в errors. Не обещать гарантированное физическое стирание копий строк в памяти библиотек.

Начальные пределы: auth result/envelope 64 KiB; каждый token/hint 16 KiB; issuer/redirect 2 KiB, subject 1 KiB, client ID 512 ASCII, host UUID строго формата, scopes суммарно 4 KiB с максимумом 64 элементов. Callback/request bytes 8 KiB; authorize URL 32 KiB; metadata/JWKS/token body 512 KiB, исходящий HTTP body 64 KiB. Presence flags/UTF-8/enum/length/overflow проверяются на реальном ingress; отсутствующие optionals не содержат used spans. Длины не обрезаются. Ручная пауза и отключённый анализ не запускают чтение источников или model network от изменения auth UI.

## Приёмка

TDD: bounded transport (chunked oversize/stall/redirect/retry), прежний reactor panic при включённом read_timeout, медленное тело с отдельной проверкой read/total сроков, удержание busy до настоящего cleanup при задержанном test-only resolver, real local HTTP listener/parser, PKCE/state/nonce и динамический issued ID до exchange, неизвестный исход/pending повтор, invalid/missing signature/claims/scopes/refresh, точная binding returning, один POST при double call/маленьком output buffer, refresh prepare failure сохраняет запись, удаление credential failure запрещает POST, rotating unknown не повторяется, cancel/logout fence и фактическое завершение, запуск/перезапуск с cached session без браузера, bounded bad persisted data без сброса, no secrets в ошибках. Test-only IdP/JWKS/keys и doubles допустимы; production fake provider нет. Изолированный временный Keychain проверяет собственные CRUD, не читает пользовательские записи и не меняет default/search list. Если системный доступ блокирует такую проверку — честно BLOCKED, не смягчать ACL.

Дополнительные регрессии: обязательный неизменный `ext_agent_host_id` в initial и returning URL; повторный запуск находит тот же envelope по фиксированным service/account и сохраняет UUID; повреждённая/недоступная запись не создаёт новый UUID/регистрацию; истечение пяти минут блокирует dispatch и поздний commit без преждевременного освобождения занятой операции.

Нужны Type Scaffolder read-only, Localization Mechanic EN/RU, Endpoint Registry Mechanic для проверенных endpoint-констант (важный протокол остаётся Sol), Code Simplicity Review, полный yarn verify, macOS build/signature и сохранность checkpoints 06/07A/07B. Нативный вход пользователя/refresh, визуальный UI, Windows, Fast/G5 и полный06 отдельно не заявлять пройденными. Новый scope требует module README и обновления product/privacy/contracts/status в том же изменении.

## Проверенные основания

## Уточнение транспорта по реальному TDD

19 октября2026 Sol06B воспроизвёл panic `no reactor running` в reqwest0.12.28 `async_impl/body.rs:346` при blocking чтении с read_timeout; удаление read_timeout устраняло panic, но нарушало заданный срок. Узкий Pattern Librarian и независимый Plan Simplicity Reviewer подтвердили причину. Поэтому выше выбран async reqwest внутри одного синхронного call, без изменения auth ABI, владельца credentials, внешних сроков/лимитов, счётчиков или запрета model calls. Это внутренняя техническая поправка в рамках поручения автономно разрешать проблемы, не новое продуктовое поведение. DNS cleanup может продолжиться после deadline и не считается завершённым раньше действительного возврата. Новые проверки обязательны до приёмки; библиотечное чтение исходников не заменяет их.
