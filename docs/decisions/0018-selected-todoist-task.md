# ADR-018: выбранная задача Todoist

Статус: **пересмотр на общем движке интеграций — проект, 20 октября 2026.** Прежний проект 17A (отдельные схема, ABI и жизненный цикл) прошёл Finished Plan Review и Evidence Audit, но устарел после [ADR-019](0019-unified-integrations.md) и принятия [ADR-020](0020-integration-layer-contract.md) (23A–23C). Эта редакция делает Todoist третьим HTTP-адаптером общего движка и пятой встроенной интеграцией. Предметные требования сохранены; механику даёт движок. Решение D65: аккаунт записывается в профиль один раз. D66: срок ожидания после 429/503 берётся из заголовка и тела ошибки, больший. D67: конечный `GET /user` убран. Finished Plan Review и Evidence Audit выполнены, замечания внесены; повторные проверки исправленных частей обоими специалистами — без опровергнутых утверждений и без вопросов к пользователю, их уточнения внесены (см. «Решения обзоров»). **Редакция принята для задачи 17A 21 октября 2026**; реализация — после приёмки 24A. Прежняя редакция: `target/verification/orchestration/0018-before-engine-revision.md`. Full17/G6, реальные права, тариф, история и UI остаются открытыми.

## Problem Statement

Личные задачи Todoist ещё нельзя явно связать с сохранённым делом и использовать в существующей помощи. Нужны проверяемое происхождение и честные границы доступности, без записи в Todoist и специального каталога сценариев.

## Solution

Пользователь подключает личный API token, выбирает активную задачу по ID и явно читает её, сведения проекта и ограниченные комментарии. Затем выбирает 1–32 объекта, проверяет точный набор и сохраняет его в общее дело. Помощь 08B использует сохранённые факты по прежнему отдельному допуску. Todoist — встроенная интеграция (D60): её можно выключить в «Настройки › Интеграции» (D61).

Личный token может иметь права записи. Приложение выполняет только фиксированные операции чтения; оно не утверждает, что сам token read-only. OAuth data:read существует, но production-native callback пока не подтверждён. Для личного среза выбран документированный personal-token путь без refresh и backend.

## User Stories

1. Подключаю личный token и вижу честную информацию о его правах.
2. Выбираю одну активную задачу, не импортируя весь аккаунт.
3. Получаю сведения проекта и комментарии без обхода соседних задач и ссылок.
4. Вижу, что активная задача не заменяет историю завершённых задач.
5. Различаю отсутствующее, null, ошибочное поле и пустой текст.
6. Сохраняю точный выбранный набор с происхождением одной операцией.
7. Обсуждаю факты в существующей08B вместе с другими источниками.
8. При обновлении фактов прежнее обсуждение остаётся явно устаревшим.
9. Отзыв ключа или исключение аккаунта очищает зависимую помощь.
10. Повторное подключение аккаунта не восстанавливает забытые сведения.
11. Общая задача не отвергается из-за другого владельца; авторство не выдумывается.
12. Прерываю чтение без скрытого продолжения и автоматического повтора.
13. Состояние Todoist не завершает дело Ambient автоматически.
14. Срок и часовой пояс остаются наблюдёнными данными без выдуманной конвертации floating времени.

## Implementation Decisions

### Владение и место в движке

Todoist — третий HTTP-адаптер движка [ADR-020](0020-integration-layer-contract.md) после GitHub и Jira (`ADAPTERS` из трёх элементов) и пятая встроенная интеграция: вид интеграции `todoist`, номер вида в ABI интеграций v1 — 5, пятый переключатель. Своих таблиц, ABI, жизненного цикла чтения, окна, предпросмотра и сохранения у Todoist нет: их даёт движок, как Jira и GitHub. Адаптер владеет только предметной частью: целью, последовательностью запросов, разбором ответов, проекцией, проверками identity, покрытием категорий, метаданными и реакцией на ошибки Todoist.

Что добавляется в общий код:

- Core: вид `IntegrationKind::Todoist` и `BuiltInIntegration::Todoist`, пустые настройки `IntegrationConfig::Todoist({})` (`deny_unknown_fields`), варианты цели, запроса, покрытия и метаданных Todoist, запись в таблице адаптеров (`adapter(kind)` желательно выводить из `ADAPTERS`, чтобы адаптер регистрировался один раз), пятая строка начального заполнения переключателей и новая `user_version` в `memory_store.rs`. Места с числом видов: проверка `user_version` в `inspect_schema`, `switches != 4` и его комментарий в `validate_integrations`, `IntegrationKind::as_str/parse` (`as_str` → `"todoist"`: под этим ключом сведения попадают к модели), `ADAPTERS: [_; 3]`, `adapter(kind)`. Числа (версия схемы, переключатели, адаптеры) исполнитель перечитывает после 24A.
- Следующая версия схемы после принятой к началу работы (после 24A): вид `todoist` допускается в CHECK трёх таблиц интеграций; переключателей ровно пять. Прежняя схема отклоняется только для чтения, включая WAL; её fixture замораживается до правки `schema.sql`.
- Providers: реестр Todoist — фиксированный хост `api.todoist.com:443`, путь `/api/v1`, Bearer, `Accept: application/json`, фиксированный User-Agent; извлекается заголовок `Retry-After`; неоднозначные при переполнении заголовков статусы 401/429/503; новое поле реестра `error_body: &'static [u16]` — `&[429, 503]` у Todoist и `&[]` у Jira и GitHub (см. «Пауза сервера»). Ветвления по виду в транспорте нет. `authorization()` получает ветку `(GitHub | Todoist, None)`, `route()` — ветку Todoist.
- Bridge: `AMBIENT_INTEGRATION_TODOIST 5u`; один типизированный экспорт сохранения профиля Todoist без аргумента `scope` (аккаунт записывает движок, см. ниже). Экспорты исключений, переключателей, чтения, окна, предпросмотра и сохранения работают для вида 5 без изменений.
- macOS: вид и переключатель Todoist (`titleKey`), `IntegrationConfig.todoist`, секрет `todoistToken` в общем владельце секретов, адаптер источника на общем каркасе и типизированное сохранение, модель метаданных Todoist и вариант `IntegrationCitation` (`SelectedAssistance.swift`), представление метаданных в карточке помощи (`AssistanceCardView.swift`), владелец источника Todoist в `AssistantModel` с `cancel()`/`close()` по образцу Jira, раздел в `AssistantView` (включая выключенное состояние), место в `AssistantSettingsView`, строки EN/RU. Новые файлы `TodoistSources.swift` (адаптер, черновик, модели метаданных) и `TodoistSourcesView.swift` (представления объекта, покрытия и метаданных, соответствие `IntegrationPresentation`, `TodoistSettingsView`) по образцу Jira; в `IntegrationSources.swift` — namespace `todoist-api-v1` → `.todoist` и ветка конфигурации профиля. `IntegrationSecret.todoistToken` повторно использует ключи кодирования и проверку формы `githubToken`. Core 08B не ветвится по виду; в Swift такие места есть, и они перечислены здесь. Без варианта цитаты и представления в карточке сведения Todoist не видны в 08B.

Запрещены сброс личной памяти, второй Store или планировщик и отдельный чат.

### Профиль, секрет и аккаунт

Профили, ревизии, поколения доступа, пауза сервера, исключения, замена и отзыв ключа, завершение удаления после очистки Keychain и отзыв ровно отправленного поколения при 401 — общие правила ADR-020 (до 8 профилей и до 128 исключений на вид). Токен хранится в общем конверте Keychain, привязанном к экземпляру базы (`dev.ambient.foundation.integrations`, запись `<экземпляр>/<профиль>`), не в SQLite, контексте модели или журнале.

Форма токена — как у GitHub: печатные символы ASCII без пробелов, 1–16 KiB, вторая часть секрета пустая. Это предел приложения, не обещание Todoist; проверка «40 hex» запрещена. Приложение выполняет только фиксированные запросы чтения; оно не утверждает, что сам личный токен read-only.

**Аккаунт (D65).** Профиль Todoist сохраняется без `scope`. Аккаунт становится известен при первом `GET /user` и записывается в профиль один раз:

- Новый шаг адаптера `Step::Pin(account)` значит «продолжить, но сначала записать этот `scope` в профиль». Движок обрабатывает его в приёме ответа одной транзакцией `Store::change`: `validate_scope` адаптера, отказ при исключённом аккаунте, отказ при том же аккаунте в другом профиле (та же проверка дубликата, что при сохранении), затем `UPDATE … SET scope=? WHERE id=? AND scope IS NULL` с проверкой числа изменённых строк (защита от повторного `Pin`) и `validate_settings`. Повторно сверять версию профиля не нужно: `accept_integration_response` в том же вызове `&mut self` уже прошёл `integration_fence`, и до `change` профиль никто изменить не может.
- Ревизия и поколение не меняются: fence чтения сравнивает только ID, ревизию и поколение, у профиля без аккаунта ещё нет сохранённых сведений и оснований 08B, а чтение вида одно. Особый переход Core, обновление fence и сброс флага отмены не нужны.
- Предметный отказ записи (неверный формат, исключение, дубликат) проваливает операцию кодом 409 до запросов задачи; повторный `Pin` при уже записанном `scope` — защита от ошибки адаптера с тем же кодом 409; ошибки хранилища не маскируются и передаются дальше, как в пути 401. При откате транзакции ничего не меняется. Отмена до приёма ответа останавливает операцию раньше записи; флаг отмены не сбрасывается.
- После записи каждый следующий шаг проходит общий fence с `allowed()`: исключение аккаунта, сделанное позже, повышает ревизию профиля и отменяет чтение (защита от ABA, как сейчас).
- Правило ADR-020 «`scope` неизменяем» уточняется: `scope` задаётся при сохранении или один раз записывается движком (NULL → значение) по запросу адаптера; после этого неизменяем. Сохранение существующего профиля Todoist передаёт хранимый `scope` без изменений: экспорт сохранения Todoist читает его из Core внутри того же замыкания `store(h, …)` (ID 0 → `None`, иначе `scope` профиля) и вызывает сохранение под одной блокировкой Store. Брать `scope` из Swift нельзя: снимок `IntegrationProfile.scope` пуст, пока идёт чтение и до перечитывания профилей, а общее сохранение отвергает другой `scope` как `InvalidInput`. Запись аккаунта не меняет ревизию, которую держит UI, поэтому переименование во время чтения проходит.

`validate_scope` Todoist принимает `None` (аккаунт ещё не записан) и `Some` (записанный аккаунт); исключение аккаунта принимает только `Some`. Todoist — первый вид, у которого `scope` бывает и пустым, и заданным, поэтому комментарий трейта «вид всегда или никогда не имеет `scope`» обновляется. Формат аккаунта: непрозрачная строка 1–128 байт UTF-8 без управляющих символов, без нормализации регистра и числового преобразования (предел `scope` схемы). Превышение отклоняется до записи и до запросов задачи. Из ответа `/user` используется только ID; email, имя и настройки не сохраняются. До первого `GET /user` аккаунт нового токена неизвестен: этот запрос — явная проверка identity, а не предварительная защита по аккаунту. Закреплённый профиль принимает только свой аккаунт: другой ID в `GET /user` проваливает операцию кодом 409 без привязки. Конечного `GET /user` нет (D67): токен за время чтения не может перейти к другому аккаунту, а отозванный токен даёт 401 на конечном запросе задачи. Токен другого аккаунта требует нового профиля. `authorized` Todoist требует `profile.scope == Some(аккаунт из метаданных)`, иначе `StaleRevision` (профиль без записанного аккаунта ничего не разрешает); `same_identity` сравнивает аккаунт, вид и ID объекта — по образцу Jira.

`Task.user_id` означает владельца задачи, а не читающего; общая задача допустима. Added/assigned/responsible/completed-by/comment-author — разные роли. Project-level exclusions и browser aliases не заявляются; глобальная D40 остаётся отдельной приёмкой.

SourceKey: namespace `todoist-api-v1`, scope — проверенный аккаунт. Object ID — компактный JSON-массив строк в фиксированном порядке: `["task", task ID]`, `["project", project ID]`, `["comment", parent task ID, comment ID]`. Экранирование JSON сохраняет границы непрозрачных строк; конкатенация через разделитель не используется. Форма стабильна в namespace v1 и проверяется при открытии; общий предел SourceKey (`SourceKey::validate`) при ID ≤256 байт не достигается. Форма та же, что у Jira (`serde_json::to_string` кортежа). Тесты включают кавычки, обратную косую черту и одинаковые ID разных типов и родителей. ID — непустые непрозрачные строки UTF-8 ≤256 байт без управляющих символов, `.`/`..` и клиентских `tmp-`; числовой конвертации нет. Профиль другого владельца не перезаписывает привязку. Удаление и пересоздание профиля не меняет SourceKey и защиту tombstone.

### Чтение и ограничения

Только HTTPS `api.todoist.com:443/api/v1`, без redirects, proxy, автоматических повторов, опроса, `public_key`, Sync POST, записи, загрузки ссылок и медиа. Loopback-маршрут — только под тестовой feature. Порядок:

1. `GET /user`.
2. `GET /tasks/{выбранный ID}`.
3. `GET /projects/{task.project_id}`.
4. `GET /comments?task_id={закреплённый ID}&limit=50`, затем тот же запрос с непрозрачным cursor — не больше 5 страниц.
5. Конечный `GET /tasks/{закреплённый ID}`.

`max_requests` адаптера — 9; остальные пределы общие: 30 секунд на операцию, 1 MiB на тело и 8 MiB всего, окно ≤512 объектов и 512 KiB, запись 16 KiB, Store 64 MiB. Единственная конечная проверка — задача; общий резерв движка (1 запрос и 1 MiB) ей соответствует. На этапе комментариев адаптер соблюдает этот резерв (причина `read_limit` и переход к конечной проверке), как Jira; при пределе 5 страниц резерв по числу запросов не срабатывает, и его ограничивает только порог 6 MiB прочитанных тел.

Начальный ID задачи совпадает с выбором; ID задачи и проекта пригодны. Начальная и конечная задача: `checked=false`, `is_deleted=false`. Неизвестный или ошибочный статус не позволяет привязку. Конечные ID задачи и проекта совпадают с начальными; иначе вся привязка запрещена. ID проекта в ответе совпадает с запросом; удалённый или архивный проект не представляется активным. Nullable `updated_at` не считается ревизией, доказательством атомарности или отсутствия A→B→A. Конечная задача заменяет начальную в окне; проект и комментарии — отдельные наблюдения.

Пагинация комментариев: `results` и `next_cursor`. Null означает конец; отсутствующий или неверный cursor — partial. Cursor ≤4096 байт, непрозрачный, соответствует документированному шаблону запроса; параметры сохраняются. Повтор cursor или страницы и пустая страница с cursor прекращают чтение с partial. Порядок и «самые новые» комментарии не обещаются. Дубликат ID не дублирует запись; конфликт содержимого отмечает нестабильность и делает этот объект непригодным для привязки; остальные пригодные объекты доступны. Sparse fields не документированы: тело ограничено, проекция выбирает только нужные поля.

Отказ или неверная identity пользователя, начальной или конечной задачи запрещают привязку. 403/404 проекта или комментариев дают «категория недоступна»; остальные сведения допустимы после успешных проверок якорей. Это не доказательство удаления. 401 отзывает поколение на любой стадии (общее правило).

**Пауза сервера (D66).** Срок ожидания берётся и из заголовка `Retry-After`, и из поля `error_extra.retry_after` тела ошибки; используется больший из доказанных будущих сроков. Открытые источники не показывают, какой из них Todoist присылает при 429/503, поэтому правило не зависит от этого ([evidence](../features/assistant-behavior/evidence/17-todoist-integration-research.md)).

- **Чтение тела в providers.** `get` читает тело при статусе 200 или статусе из `registry.error_body`. Для статуса ошибки предел — 64 KiB (`MAX_INTEGRATION_ERROR_BODY` — константа providers в `integration.rs`; Core её не использует, адаптер узнаёт превышение по длине тела больше 64 KiB): транспорт читает не больше предела плюс один байт, обрезая последний chunk (`chunk()` может вернуть больше), и останавливается без ошибки. Чтение тела ошибки — по возможности: срок, отказ транспорта или достижение предела завершают его с уже прочитанными байтами, чтобы срок из заголовка не потерялся; наружу передаётся только отмена. Ошибка `Limit` (413) для этого не используется. Тело только в памяти: не сохраняется в SQLite, метаданных, окне и журналах. Пауза завершает операцию до учёта байтов, поэтому тело читается не больше одного раза за операцию и в бюджет 8 MiB не входит. Тело ошибки без паузы (503 без срока) учитывается как обычное и операцию всё равно завершает ошибкой.
- **Разбор в адаптере.** `Adapter::pause` получает весь ответ: `pause(&self, response: &IntegrationResponse, now)`; Jira и GitHub читают из него `status` и `headers`, как раньше. Адаптер Todoist разбирает `error_extra.retry_after` как неотрицательное целое число секунд. Иной тип, отрицательное значение, переполнение, неверный JSON или тело длиннее 64 KiB делают этот источник неизвестным, но не отменяют другой. Разбор JSON в providers и новое поле в `IntegrationHeaders` отклонены: это перенесло бы предметный разбор в транспорт.
- **Заголовок.** Общий метод `IntegrationHeaders::retry_after_deadline(&self, now) -> Option<i64>` разбирает целые секунды или HTTP-дату для Jira, GitHub и Todoist и не оценивает давность; наборы тестов Jira и GitHub его охраняют. Метод возвращает только `Option<i64>`: GitHub по-прежнему помечает нечитаемый `Retry-After` как недоверенный срок (`known=false`) в своём `cooldown`. Срок не позже `now` (`Retry-After: 0`, дата в прошлом) адаптер Todoist отбрасывает до выбора большего.
- **Когда пауза.** 429 ставит паузу всегда. 503 — если есть заголовок `Retry-After`, неоднозначный заголовок или ключ `error_extra.retry_after` с любым значением; иначе 503 просто завершает попытку ошибкой. Код отказа — исходный статус.
- **Известность срока.** Срок известен, если после отбора есть хотя бы один будущий срок (`known = until.is_some()`). Неоднозначный заголовок не отменяет срок, доказанный телом. Неизвестный срок не объявляется нулём. Переполнение при вычислении срока ведёт себя как у Jira.
- **Без верхнего предела.** Очень большое значение становится сохранённым сроком, который нельзя сократить, — как у Jira и GitHub; D66 велит брать больший срок, собственный предел не вводится.
- **Другие статусы.** Для 401 и 403/404 тело не читается (их нет в `error_body`); 401 обрабатывается общим правилом до паузы.
- Неизменно: собственная задержка не выдумывается; сохранённый срок нельзя сократить или обойти заменой токена (общее правило записи паузы); автоматических повторов нет; следующий явный Read проходит допуск заново.

### Проекция

Selected task: id, user_id, project_id, content, description, parent_id, section_id, added_by_uid, assigned_by_uid, responsible_uid, completed_by_uid, checked, is_deleted, added_at, updated_at, completed_at, due, deadline, duration. Для привязки задачи нужен непустой content ≤4096 байт; description ограничен записью 16 KiB. Другие поля не заявляются полным покрытием. Статус, parent и сроки не создают зависимости плана и не завершают дело Ambient.

Selected project: id, name, description, parent_id, workspace_id при наличии, is_archived, is_deleted, created_at, updated_at. Ответ — union personal/workspace объектов, не wrapper/array. Не угадывать тип по пустому полю, parent не загружать. Нет обязательной identity — нет привязки; остальные missing/null/invalid видны без подстановки.

Selected comment: id, content, posted_uid, posted_at, is_deleted и наличие file_attachment. Принадлежность задаче следует из фиксированного запроса коллекции, не из item_id: REST NoteSyncView его не обещает. Content missing остаётся missing, null — invalid, не пустая строка. Пустой текст или только вложение не превращаются в выдуманный факт и не привязываются. Наличие вложения отмечается как пропущенное; URL и метаданные не загружаются. Удалённый комментарий не привязывается, покрытие учитывает пропуск.

Content/description сохраняются как буквальный UTF-8 Markdown, отображаются как есть, без HTML/Markdown-рендеринга и активных URL. ADF parser не используется. Текст источника не является инструкцией или разрешением.

Выбранные поля сохраняют Missing/Null/Invalid/Value (собственное перечисление адаптера; общий тип с Jira не обязателен — имя типа не сериализуется, поэтому общий `Presence<T>` побайтно нейтрален и допустим по выбору исполнителя). Due/deadline/duration — ограниченные наблюдения известных подполей: due(date, timezone, is_recurring, string, lang); deadline(date, lang); duration(amount, unit). Неизвестные поля и неверная форма отмечаются потерей. Пределы: date 128, timezone 128, string 1024, lang 64, unit 64 байта; amount — неотрицательное целое в пределах i64. Date-only и floating сохраняются как такие наблюдения; UTC не выдумывается. Фиксированный RFC 3339 можно нормализовать с явной потерей точности. Именованная timezone не разрешается без базы IANA. Неверная или неизвестная дата не становится утверждением о сроке. Остальные отметки времени — nullable RFC 3339 с раздельными missing/null/invalid; разбор — `time::OffsetDateTime::parse(.., &Rfc3339)`, как у Jira, GitHub и Codex, без нового парсера.

Метаданные: профиль, ревизия, поколение и аккаунт; вид, identity и родительская задача; проекция, presence и потери; локальный интервал и покрытие категорий; `non_atomic_observation`/`current_state_unverified`. Версия — канонический хэш стабильной identity, содержимого и семантической проекции с presence и потерями по образцу `content_version` Jira (метка, части с длиной, сериализованное типизированное содержимое); профиль, поколение, время чтения и покрытие пагинации её не заменяют. Открытие проверяет метаданные, SourceKey, хэш и размер через `validate_metadata`/`validate_object` адаптера.

### Сохранение и помощь

Предпросмотр, сохранение 1–32 объектов одной транзакцией, защита ручных правок и tombstone, устаревание обсуждения 08B при обычном обновлении, атомарная очистка зависимой помощи (включая основания без цитат) при исключении, отзыве ключа, удалении профиля и выключении интеграции, пауза, срок сессии, отмена и освобождение после фактического завершения транспорта — общие правила движка. Импорт не запускает модель.

Промпт модели не меняется: он уже требует считать весь ввод недоверенными данными и не выводить выполненную работу; сведения Todoist попадают к модели под ключом `todoist` общим путём 08B. История 13 (состояние Todoist не завершает дело Ambient) обеспечена отсутствием записи и отсутствием логики завершения по статусу. Эталонное тело запроса помощи без Todoist остаётся побайтно прежним.

Native UI использует общий каркас источника, «Настройки › Интеграции» и 08B: профиль и токен, выбранный ID, Read/Refresh/отмена, ограничения категорий, выбор, предпросмотр и сохранение, исключение аккаунта, замена и удаление секрета. Записанный аккаунт виден после чтения без доработки: общая модель источника уже перечитывает профили в конце чтения. Все состояния EN/RU; чувствительную формулировку утверждает оркестратор до Localization Mechanic.

## Testing Decisions

Настоящий локальный путь: временная SQLite → C → Swift → изолированный Keychain → loopback HTTP → точный набор → 08B. Production mocks запрещены. Логика меняется через RED/GREEN; code simplicity review после готовности.

Core (сценарии ответов в стиле `core/tests/integration_engine.rs`):

- первое чтение: после `GET /user` у профиля записан `scope`, ревизия и поколение прежние, флаг отмены не установлен, следующий шаг допущен;
- исключённый аккаунт: 409, ни одного запроса задачи, `scope` пуст; исключение после записи отменяет чтение через повышение ревизии;
- тот же аккаунт в другом профиле: отказ, другой профиль не затронут; слишком длинный или неверный ID: записи нет;
- закреплённый профиль и другой аккаунт в `GET /user`: 409, привязки нет; повторный `Pin` при уже записанном `scope`: 409; ошибка хранилища при записи не превращается в 409;
- переименование закреплённого профиля (в том числе во время чтения) проходит: экспорт передаёт хранимый `scope`;
- отмена до ответа `GET /user`: записи нет, флаг остаётся;
- из ответа `/user` сохраняется только ID: тело (в нём по спецификации есть `token`, `email`, `websocket_url`) не попадает в SQLite, метаданные и журналы;
- не больше 9 запросов при 5 страницах комментариев; резерв конечной проверки задачи по порогу 6 MiB (тела около 1 MiB);
- пауза сервера — модульные тесты `pause` Todoist на синтетических `IntegrationResponse`: 429 с заголовком, с полем тела, с обоими (берётся больший), без обоих (срок неизвестен); `Retry-After: 0` и дата в прошлом отбрасываются; неверное поле при верном заголовке и наоборот; неоднозначный заголовок не отменяет срок из тела; 503 с заголовком, с ключом тела (даже неверным), с неоднозначным заголовком и без них; тело длиннее 64 KiB;
- сырое тело ошибки нигде не сохраняется: 429 с меткой-канарейкой в теле, затем поиск метки в файле SQLite, WAL, окне и JSON метаданных;
- 401 отзывает только отправленное поколение;
- общий метод `retry_after_deadline`: наборы Jira и GitHub без изменений;
- одна сквозная проверка Todoist → сохранение → 08B; сохранение и отзыв 08B повторно используют наборы движка;
- прежняя схема отклоняется без записи, включая WAL; база с 4 или 6 переключателями не открывается;
- фиксированные GET и принадлежность: loopback-запись точных путей и параметров (нет записи, `public_key`, Sync POST) и существующий тест отсутствия redirects; перемещение задачи и конечная identity задачи; циклы, отсутствие и пустые страницы cursor; большие и chunked тела;
- буквальный Markdown, неизвестное расписание, date-only, null, invalid, только вложение, удалённые; частичные категории и фатальные якоря; канонический хэш и открытие.

Providers (loopback): тело читается только для 429/503 Todoist, предел 64 KiB соблюдён, остановка чтения тела по сроку сохраняет заголовок, Jira по-прежнему тело ошибки не читает; отмена во время чтения тела ошибки возвращает `Cancelled`, а не срок или отказ транспорта; для 401/403/404 и для Jira/GitHub тело не читается; существующий режим `error-body` остаётся зелёным; ветка `authorization()` для Todoist (вторая часть секрета — отказ).

Bridge: вид 5 принимается экспортами профилей, исключений и переключателей (прежний тест, ожидающий отказа для видов 0 и 5, и комментарий заголовка «виды 1..4» меняются); раскладка нового экспорта сохранения; непустая вторая часть секрета Todoist — `INVALID_ARGUMENT` и прерывание операции; число экспортов +1.

Swift: наборы `IntegrationSourcesTests` и `IntegrationSwitchesTests` получают Todoist; loopback `GET /user` → задача, проект, комментарии → предпросмотр → сохранение → 08B; конверт `todoistToken`; пятый переключатель; цитата и карточка 08B с метаданными Todoist. Наборы GitHub, Jira, `integration_switches` и `selected_assistance` остаются зелёными; эталоны JSON побайтно прежние.

Общие сценарии движка (выключение, отмена, срок сессии, ABA при 401) остаются проверенными на GitHub и Jira; для Todoist они подтверждаются сквозной проверкой и названными выше тестами, без параметризации всех наборов по адаптеру.

Обязательны verify tooling/core/Swift, feature integration, all-features Clippy, сборка, подписи, хэши исходников и неизменность контрольных сборок по базе, которую оркестратор фиксирует перед запуском. Без живой модели, Jev, аккаунтов, UI, TCC, микрофона и ServiceManagement.

## Решения обзоров

20 октября 2026, Finished Plan Review (Plan Simplicity Reviewer) — PASS с исправлениями, Evidence Audit — подтверждённые утверждения, исправления внесены:

- Todoist — третий HTTP-адаптер и пятая встроенная интеграция (не «пятый адаптер»).
- `Pin` без повторной сверки версии (fence уже пройден в том же вызове), с проверкой числа изменённых строк; 409 только для предметных отказов.
- Хранимый `scope` при сохранении читается в мосту из Core, не из Swift.
- Конечный `GET /user` убран решением пользователя D67; `max_requests` 9, расхождение резерва 2 MiB/1 MiB исчезло.
- Тело ошибки: поле реестра `error_body`, предел 64 KiB, чтение по возможности, `Adapter::pause` получает ответ, разбор в адаптере; общий метод `retry_after_deadline`; отбор будущих сроков и `known = until.is_some()` в адаптере Todoist; без верхнего предела срока.
- Промпт модели не меняется.
- Добавлены места Swift (цитата, карточка, `AssistantModel`, `AssistantView`, настройки), начальное заполнение переключателей и `user_version`, тесты моста для вида 5, раздел «Документация».
- Удалены невозможные требования: бюджет 8 MiB для тела ошибки, игнорирование `retry_after` на 401/403/404 (тело не читается), предел 2048 байт SourceKey; перечитывание профилей уже делает общая модель.
- Повторное использование: форма ID и `content_version` как у Jira, RFC 3339 через `time`, ключи кодирования `githubToken`.

Повторные проверки исправленных частей (21 октября 2026): Evidence Auditor — опровергнутых утверждений нет; уточнены запись ADR-020 о `Pin`, места с числом видов, расположение константы предела тела ошибки и обрезка последнего chunk, сохранение `trustworthy` у GitHub. Plan Simplicity Reviewer — PASS с исправлениями: правила `authorized`/`same_identity`, файлы Swift Todoist, учёт тела ошибки без паузы, формулировка 503 в задаче, тесты отмены чтения тела, повторный `Pin` как защита от ошибки адаптера.
