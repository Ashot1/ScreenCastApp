# Ambient Core

## Управляемый сервер Google (24B / ADR-022)

`ServerKind::Managed { id: ManagedServerId }` (`{"kind":"managed","id":"google-workspace"}`) и `Target::Managed(id)`; `needs_key()` всегда истина, `downloads_code()` ложь. `ManagedServerId` — одно перечисление (`GoogleWorkspace` ↔ `google-workspace`, `as_str`/`parse`), на нём построены исчерпывающие `match`: список разрешённых инструментов `allows()` (Core), встроенный пакет `builtin_package()` (`include_bytes!` из `builtin/google-workspace/{plugin.json,mcp.json}`) и `builtin_package_hash()` (константа; тест сверяет её с хэшем байтов — расхождение при выпуске даёт громкий отказ), рецепт и реестр OAuth в providers. Запись `{"ambient_managed": "<id>"}` даёт `Managed` только в пакете с хэшем встроенного (`servers(bytes, hash, …)` в `parse_package`, то есть при просмотре и установке); в любом другом пакете или с неизвестным ID — предупреждение и пропуск; вместе с другим членом записи — отказ пакета. При открытии сохранённый `Managed` проверяется только структурно, поэтому новая версия встроенного пакета не делает установленный плагин неоткрываемым. Список разрешённых имён (8: `search_drive_files`, `get_drive_file_content`, `list_drive_items`, `search_docs`, `get_doc_content`, `get_doc_as_markdown`, `list_docs_in_folder`, `list_document_comments`) проверяется при одобрении (`InvalidInput`), в JSON обнаружения (`discovery_json(&Discovery, &Target)` ставит `approvable:false`) и при каждой выдаче разрешения (конверт `not_allowed` без сети и без строки журнала; схема 15 не меняется). Первый вызов управляемого сервера в запросе получает запас 120 s, как локальный; без ключа — `login_required`. Тесты: `tests/managed_server.rs`, unit `plugin_loop_tests.rs` (запас 120 s).

## Локальные серверы плагинов (24C / ADR-022)

Сервер пакета — `PluginServerSpec { key, kind: ServerKind }` с явной меткой `kind`: `Remote { url, auth_required }` или `Local { command, args, env }` (`env` — только имена; значения приходят секретом `env(map)` из Связки ключей). Нужен ли ключ, выводит `needs_key()`; `downloads_code()` отмечает команды, скачивающие код при каждом запуске (D70: `npx`, `bunx`, `uvx`, `pnpm dlx`, `yarn dlx`, `pipx run`); `target()` даёт `Target { Remote { url } | Local { command, args, env_names } }` для разрешения вызова и обнаружения — providers пакет не читает. Разбор (`plugin_package.rs`): запись с `command` (`type` нет или `stdio`) — локальная; `url` вместе с `command`, команда вне 1…1024 байт, >32 аргументов или аргумент >1024, >16 имён, имя не `^[A-Z_][A-Z0-9_]{0,63}$`, `PATH`/`HOME`/`TMPDIR`/`DYLD_*`/`LD_*`, NUL — отказ пакета; команда с относительным путём (папка пакета) — предупреждение и пропуск; `cwd`, `${VAR}` и относительные пути в аргументах — предупреждения. `local_kind` — один проверяющий конструктор для установки и проверки при открытии; сохранённый пакет прежней плоской формы или с неверным локальным сервером даёт `UnsupportedSchema`. JSON просмотра и списка: сервер `{key, kind, needs_key, downloads}` (+`generation` в списке), одна точка сборки `server_json`. Запас перед вызовом: 90 s (`CALL + FINAL_MARGIN`), для первого вызова локального сервера в запросе (`list_first`) — 120 s (`+ LOCAL_START` 30 s на запуск и `initialize`). Локальный сервер без значений — «не настроено» без сети и без строки журнала. Новые исходы `NotConfigured = 10` (недостающее имя в карте секретов) и `StopUnconfirmed = 11`: `record_unconfirmed_stops` после запроса ставит его на последнюю строку журнала вызовов сервера. `Discovery { listed, stderr, stop_confirmed }` и `discovery_json` (статусы `not_configured`, `cancelled`; `stderr` только при отказе; `stop_confirmed: false` при неподтверждённой остановке). Schema15: единственное изменение — `plugin_calls.outcome` 0..11; schema14 и её WAL отклоняются read-only (fixture `tests/fixtures/schema-fourteen.sql`). Тесты: `tests/plugin_package.rs` (локальные записи и пределы), `plugin_lifecycle.rs` (схемы 13/14, сохранённая форма, JSON обнаружения), `plugin_loop.rs` (цель, «не настроено», неподтверждённая остановка), unit `plugin_loop_tests.rs` (запас 120 s).

## Пользовательские плагины (24A / ADR-021)

Schema14 добавляет `plugins` (ID и ревизия из `local_source_clock`, `enabled`, имя ≤256, версия ≤64, хэш пакета 32 bytes, неизменяемый проверенный JSON пакета ≤256KiB), `plugin_servers` (ключ `^[a-z0-9-]{1,32}$`, поколение доступа), `plugin_tools` (закреплённое каноническое определение ≤16KiB и его SHA-256), `plugin_calls` (кольцо 256, стадии 1→2, после перезапуска стадия 1 — «прервано», строка переживает удаление плагина) и `connection_check_totals`. Schema13 и её WAL отклоняются read-only (fixture `tests/fixtures/schema-thirteen.sql`). `plugin_package.rs` — чистый разбор обоих форматов (`plugin.json`/`mcp.json` и `.codex-plugin/plugin.json`/`.mcp.json`, `skills/*/SKILL.md`): только удалённые `https` к именованному хосту (stdio/sse/без `url`/IP/localhost/userinfo — предупреждение и пропуск; ноль серверов, неверный ключ сервера, >4 серверов, >8 skills, >12KiB на skill, >48KiB skills — отказ), заголовки и секреты пакета игнорируются; хэш пакета — SHA-256 по файлам, отсортированным по пути, с префиксами длины; `canonical_tool` даёт `{name, description, inputSchema, readOnlyHint}` с сортировкой ключей (serde_json без `preserve_order`) — одобрить можно только `readOnlyHint: true` ≤16KiB. `plugin_store.rs` — установка повторным разбором с ожидаемым хэшем, список, журнал вызовов, одобрение (новое закрепление не меняет ревизию, идентичное — no-op, изменённое и снятие повышают), включение (выключение повышает ревизию; то же значение — до `Store::change`), отзыв ключа (поколение и ревизия — одно значение часов), удаление (begin: выключить и отозвать все серверы; finish: только при той же ревизии и выключенном плагине), предложение инструментов при подготовке помощи и проверки сохранённых результатов. Плагин — не вид интеграции: собственная таблица, а метаданные сохранённых результатов — общая `integration_metadata` с namespace `plugin` (зарезервирован общим `reserved_namespace`).

`plugin_loop.rs` — цикл в одном dispatch: `begin_model_loop` берёт допуск по значению, `dispatch_model_step` допускает каждый POST по ссылке через общий `dispatch_attempt` (прежний `dispatch_check` — обёртка для проверки подключения) с записью строки попытки до POST; ≤5 POST по ≤60s, ≤8 вызовов, весь цикл 180s; последний POST без инструментов, если он пятый, вызовы исчерпаны, осталось <70s или ещё один результат не поместится в 96KiB (или пересылаемые элементы — в 256KiB); вызов допускается только при ≥90s. Ошибки без сети (нужен вход, изменённое определение, неизвестный инструмент, аргументы >2KiB, пределы) возвращаются модели в конверте результата `{tool_result_id:"tool:N", tool, error}`; удачный — `{…, untrusted:true, complete, citable, text}` (UTF-8-префикс 12KiB). 401 отзывает ровно отправленное поколение и через fence снимка отменяет запрос. Пригодность к цитированию решается при приёме (забытый ключ, правка пользователя, 32 − выбранные, 256KiB контекста, `byte_room`, резерв строк). `publish` сохраняет процитированные `tool:N` через `write_source(explicit=None)` с растущей TaskVersion; забывание или правка между приёмом и публикацией — `StaleRevision`, место — `ResourceLimit`, частичной публикации нет. Основание 08B `Plugin` пригодно, пока плагин существует и включён; выключение и удаление очищают зависимую помощь, повторное включение возвращает пригодность. Журнал попыток держит ≤4096 живых строк; старые завершённые сворачиваются в итог своего назначения с суммами известных токенов и числом неизвестных (строки стадии 1 не сворачиваются). Без включённых плагинов с одобренными инструментами контекст и запрос побайтно прежние. Тесты: `tests/plugin_package.rs`, `plugin_lifecycle.rs`, `plugin_loop.rs`, `connection_check.rs`, unit `plugin_loop_tests.rs`.

## Переключатели интеграций (23C / D61)

Schema13 добавляет `integration_switches` — ровно четыре строки (`local-projects`, `codex`, `github`, `jira`), все включены при создании; при открытии другое число строк — `UnsupportedSchema` (проверка в `validate_integrations`). Schema12 и её WAL отклоняются read-only (fixture `tests/fixtures/schema-twelve.sql`). `BuiltInIntegration` — отдельный вид переключателя; `IntegrationKind` остаётся видом HTTP-движка. `set_integration_enabled` при том же значении возвращается до `Store::change` и ничего не меняет; иначе одна транзакция `change`: `clear_revoked` очищает зависимые области 08B (включая непроцитированные основания), а последующие `invalidate_stale_*` навсегда отменяют операции выключенного вида через их fence. Ревизии, поколения, профили и Keychain не меняются, сведения остаются. Проверка «включено» (`integrations::enabled`, ошибка `StaleRevision`) стоит в допуске local/Codex/интеграций, в `source_fence`/`codex_fence`/`integration_fence` (шаг, приём, окно, предпросмотр, сохранение), в транзакции сохранения интеграции, в начале `source_settings_fence` и `source_authorization_fence` для Git/Codex/Integration (через `snapshot_fence` — и в `publish`) и при сборке нового предпросмотра помощи. `invalidate_stale_source`/`invalidate_stale_codex` вызывают `source_fence`/`codex_fence`, как `invalidate_stale_integrations`. Включение снова пропускает сохранённые сведения с прежними ревизиями; очищенные обсуждения и отменённые операции не возвращаются; изменения настроек, ключа или исключения во время выключения действуют по обычным правилам. Тесты: `tests/integration_switches.rs`.

## Постоянная помощь (08B / ADR-015)

Версии среза08B: schema8/model ABI4; memory3/auth1/local-source1/Codex1 сохранены. Схемы1–7 отклоняются до записи через принятый WAL-aware `mode=ro&readonly_shm=1`; миграции, reset и sidecar-хранилища отсутствуют. Описанные ниже результаты06F/08A/14A относятся к прежним срезам; текущий владелец предложений — постоянная область08B.

В прежнем Store на дело хранится одна область: TaskVersion, точные выбранные EvidenceId, все типизированные разрешения источников, атрибутированные пары и полный набор предложений. Тексты Evidence/плана не архивируются. Отдельная `tasks.assistant_workspace_revision` повышается при публикации/очистке, включая пустой набор, и остаётся на tombstone. `assistant_proposals.id` использует SQLite AUTOINCREMENT без сброса sequence. Историческая ссылка пары на предложение не требует живой карточки; `reply:<task>:<workspace-revision-before-publication>:<pair-index>` сохраняется между запусками.

Continue включает весь набор, закрытие и диалог. NewContext включает только текущую явно выбранную память; успех полностью заменяет область и показывает новые предложения, ошибка сохраняет прежние. Preview не пишет БД/ledger и не отправляет HTTP. После прежнего учёта расхода одна Immediate-транзакция повторно проверяет версии/разрешения, применяет весь набор и сохраняет свежую visibility. Публикация не меняет TaskVersion. Model IDs сопоставляет модель; Core отвергает чужие/повторные, но не проверяет качество смыслового сопоставления.

Обычная правка даёт stale, без развёрнутых новых оснований. Удаление/забывание, завершение и смена использованного source setting очищают всю зависимую область в той же mutation-транзакции, включая непрoцитированные основания. Обычное обновление Codex ordinal/content сохраняет stale-область и пары; для удержания проверяется разрешение источника, для действий — прежний полный fence. Пауза/потеря сессии снимают процессный допуск, сохраняя область. Feed/details читаются без High и без model transport; copy/show/Continue требуют свежего допуска и проверки оснований.

Пределы:16 предложений на дело/128 всего, включая hidden/stale;32 пары;32 выбранных Evidence. Общие64MiB включают все новые переменные строки и сериализованные ссылки. До commit проверяются точные JSON-проекции с framing/metadata: feed4MiB, строка32KiB, details с развёрнутыми citations256KiB. Любое переполнение отвергает весь ответ, сохраняя прежнюю область и уже учтённый расход. При открытии проверяются связи, размеры, исторические IDs, source ownership и optional StepId через составной FK к строке шага, включая tombstone.

Локальные доказательства и ограничения: `target/verification/08b/`. Они не подтверждают native UI/focus/Spaces, macOS14 hardware, Windows, live High Fast или semantic ID quality; полный08/09 остаётся открытым.


## Выбранная сохранённая история Codex (14A / ADR-014)

Текущая схема7 добавляет `codex_selections` и typed metadata на существующий source binding; memory3/auth1/source1/model3 сохранены, новый отдельный Codex ABI1 использует тот же Store. Частичные и oversized записи видимы как потери; append требует Refresh. Никакого полного архива, auto scan/poll/Codex CLI/app-server или чтения referenced rollouts.

Bind одной Immediate-транзакцией сохраняет SourceFact, version hash, typed identity, accepted ordinal/provenance и task revision. Typed Git/Codex fences проверяют все основания, включая непрoцитированные, в prepare/dispatch/result/copy/follow-up.

Схема6 отвергается без миграции/reset. Существующая БД проходит полную WAL-aware проверку через `mode=ro&readonly_shm=1`: схема7 только в WAL принимается, старая схема отклоняется без изменения DB/WAL/SHM. Отсутствующий SHM и требующий восстановления rollback journal дают `Storage` без создания sidecar или recovery. Прямое открытие writable SQLite вне Store в том же процессе может разделять writable SHM node и не покрывается этой гарантией; предыдущая версия приложения моделируется отдельным тестовым процессом.

Один Rust crate владеет постоянной памятью для обеих платформ; unsafe запрещён. Срезы ADR-004/005 хранят несколько дел, заметки, типизированные сведения источников, явные связи/исправления и отдельную глобальную ручную паузу. ADR-005 добавляет ручной план, завершение с очисткой подробностей и независимое отключение инициативы. SQLite настоящая: `rusqlite = 0.40.2` с `bundled` (SQLite 3.53.2). Каждая мутация проверяет ожидаемые ревизии затронутых дел и одной `Immediate`-транзакцией повышает их ровно один раз. Удаление сначала выдаёт постраничный `deletion_impact`; при записи Core заново вычисляет точный набор дополнительных дел и сверяет все `TaskVersion`. Ручная пауза ревизии дел не меняет. Поздние операции и удалённые ID явно отклоняются.

Ручная заметка имеет `Origin::User`, UTC-время действия пользователя и подтверждённый текст. Внешнее сведение содержит точный `SourceKey(namespace, scope, object_id)`, отдельную необязательную версию, необязательное внешнее UTC-время, полноту и вид утверждения. Подключений сервисов нет; контракт проверяется синтетическими входами только в тестах. Одна пара `(дело, точный ключ)` обновляется с сохранением ID.

Удаление очищает текст, исходные ключи и производные/решения, сохраняя заранее выделенные строки ID и 32-байтовые отпечатки известных ключей. SHA-256 (`sha2 = 0.11.1`, без default features) считает байт версии кодирования `1`, затем три поля UTF-8, каждое с длиной `u32` big-endian; текст и версия объекта не хешируются. Отпечаток не является шифрованием. История забытого ключа возвращает `Forgotten`; существующая независимая живая привязка не стирается. Новая явная привязка к новому делу принимает только переданное новое содержание и не восстанавливает удалённый ID.

Лимиты: текст 1–16 384 точных UTF-8 байт (включая NUL); ключ без NUL: namespace 64, scope 256, object ID 2 048, присутствующая версия 256 байт. Максимум 1 024 живых дела и 100 000 строк каждого вида (дела, сведения, привязки, решения), включая отметки и резервные слоты. Сумма сохранённых текстов и исходных ключей — 64 MiB. Достигнутый предел не запрещает удаление и не вытесняет отметки. Страницы дел, сведений, источников, связей и решений — до 50 элементов и 256 KiB вместе с метаданными ABI; продолжение по стабильному ID, меньшая страница допустима. Связь несёт текст/ревизию другого дела для отображения и проверки свежести.

Затем допустимая схема проверяется вновь при открытии записи. Автоматических миграций, сброса, скрытой смены пути или слоя совместимости нет. Определения объектов схемы сравниваются точно, сохранённые ограничения/ссылки/размеры/отпечатки проверяются при открытии.

Для записи проверяются `foreign_keys=ON`, `journal_mode=DELETE`, `secure_delete=ON`. Прикладного архива нет; это логическое удаление, не обещание стирания SSD/backup. Ошибки не включают содержание или пути. Каталог выбирает native shell. Решения: [ADR-004](../../docs/decisions/0004-multiple-tasks-and-source-memory.md), [ADR-003](../../docs/decisions/0003-foundation-storage-and-native-boundary.md).

## Ручной план и жизненный цикл (ADR-005)

`Task` хранит `open/completed`, независимый `initiative_suppressed` и полноту плана. Новое дело — open/unknown. `plan_store.rs` расширяет тот же Store, транзакции и ревизии; второго хранилища/планировщика нет. При complete `steps` вычисляет все доступные незавершённые шаги: предшественники завершены и их проверки passed. Собственные проверки ограничивают завершение шага, но не его начало. Partial/unknown не рекомендуют следующий шаг; ручное подтверждение возможно при известных выполненных зависимостях и собственных passed-проверках. Пустой план не завершает дело.

Один план ограничен 64 шагами, 8 проверками на шаг и 512 рёбрами; цикл, дубли, чужие/удалённые ID и удаление шага со связями отвергаются. Обход SQLite CTE использует одну колонку ID, UNION и scope дела; LIMIT 65 — sentinel отказа, а не усечённое доказательство отсутствия цикла. Правки структуры делают план partial и сбрасывают затронутые подтверждения/проверки и потомков; результат passed→failed остаётся failed у явно изменённой проверки. Пользовательское время UTC — единственное подтверждение шага/проверки. Готовность не хранится.

`completion_impact` и `complete_task` используют один предикат удаляемых решений. Выбранные уже существующие полезные связи исключены; удаляемые решения по сведениям включены. Точный набор чужих ревизий пересчитывается внутри Immediate-транзакции и повышается по одному разу. Итог заменяет намерение, выбранные точные ссылки (до 32, 1..2048 UTF-8 без NUL) сохраняются; сведения, сырые ключи, план/промпты и ненужные решения очищаются. При проверке 64 MiB учитывается конечное содержание; любой отказ откатывает всё. Completed отвергает новые заметки/план, импорт, bind и перемещение сведений внутрь с TaskCompleted. Reopen сохраняет итог, полезные связи/ссылки и suppression, но не возвращает старое содержание; забытые ключи остаются забытыми.

Новые виды ID также ограничены 100 000 строками, включая tombstone. Удалённые рёбра очищают оба конца, сохраняя только идентичность/владельца; удаление при заполненных лимитах не выделяет новые ID. Тексты входят в прежние 64 MiB. Страницы содержат ревизию владельца и полноту плана, полученные в одной read-транзакции; до 50 элементов/256 KiB вместе с метаданными. Memory ABIv3 заменяетv2; актуальная schema7 отклоняет1/2/3/4/5/6 read-only без миграции. Тесты используют только новые временные БД.


## Проверка подключения и помощь выбранному делу (ADR-008/010)

Один прежний `Store` и `connection_checks` обслуживают два закрытых назначения: connectivity (Luna Low/High) и selected-task assistance (только High). ## Выбранная задача Jira Cloud (12A / ADR-017)

С 23A профили, исключения, чтение и сохранение Jira идут через общий движок выше; предметная семантика ниже не изменилась. Историческое описание 12A: схема была10. Schema9 и более старые БД/WAL отклоняются read-only без миграции, восстановления или смены пути. Jira использует прежний Store, source clock, память, byte/row limits и08B; нового scheduler/ledger нет. До8 профилей имеют неизменяемый exact Cloud ID; один профиль на сайт. До128 исключённых сайтов хранятся независимо от профилей. Обе смены exclude→allow повышают settings revision, замена/отзыв email/token сначала меняет credential generation в Core.

Один явный read закрепляет initial issue ID, затем читает комментарии и хвост changelog и повторяет issue GET. Только конечные issue/relations попадают в окно; другой final ID или отказ final GET запрещают сохранение. Пределы:13GET,30s,1MiB/body,8MiB/job,512 объектов/512KiB окна,5×50 комментариев и probe+5×50 changelog. Offset проверяется как i64 для comments и i32 для changelog. Final GET резервируется, но не обходит deadline/cooldown. Rate stop сохраняет только известный Retry-After deadline; неизвестный остаётся неизвестным.401 отзывает только отправленную generation даже при устаревшем деле.403/404 категории дают explicit partial; отказ initial/final завершает job.

`jira_parser.rs` различает missing/null/invalid/empty, строковые opaque IDs, Jira даты с±HHMM и потерю долей секунды. Ограниченный ADF reader возвращает текст и явные потери, не читает ссылки/media. `subtasks` — отдельное наблюдаемое поле, без alias `sub-tasks` и обхода связанных задач. Шесть source tags разделяют issue/comment/changelog/parent/subtask/issue_link. Canonical SHA256 отделяет typed content от profile/generation/interval/coverage; сохранённые metadata входят в16KiB объекта и64MiB памяти и проверяются при open.

Exact preview1–32 объектов ничего не пишет. Save одной транзакцией переиспользует `write_source`, сохраняет ID и защищает manual corrections/tombstones/cross-profile bindings. Обычный refresh делает08B stale, сохраняя допустимый разговор. Отзыв credential/profile/site очищает все зависимые08B grounds, включая не процитированные моделью, в той же транзакции. Источники всегда partial/non-atomic/current-state-unverified; чтение не вызывает модель.
