## Локальные MCP-серверы (24C / ADR-022)

`mcp.rs` разделён: общий синхронный `Protocol<W: Wire>` (`initialize`/`list`/`call`, сверка с закреплённым при первом вызове) и два провода — `HttpWire` (прежний reqwest-код, каждый запрос — `block_on` на своём current-thread runtime операции) и `StdioWire` в `local_host.rs`. `local_host.rs` (только Unix; `local_host_other.rs` — заглушка других ОС: удалённые серверы работают, локальный «недоступен» до адаптера Windows) — единственное место запуска, обмена и остановки дочерних процессов. `LocalHost` живёт один `dispatch` или одно обнаружение: карта `(plugin, server) → Live | Failed`, ≤4 живых, ленивый запуск при первом вызове (запуск и один `initialize` за `LOCAL_START` 30 s, затем вызов 20 s). Процесс: `process_group(0)`, `env_clear()`, `PATH=/opt/homebrew/bin:/usr/local/bin:<home>/.local/bin:<home>/.cargo/bin:/usr/bin:/bin:/usr/sbin:/sbin` (`<home>` — `std::env::home_dir()`), `HOME`/`TMPDIR`/рабочая папка — частная `<root>/<plugin id>` (0700), переменные из секрета `env(map)` (`parse_env_map`: повторы, имена вне разрешения, >16 имён, значения вне ASCII 33…126 после разбора JSON — `Invalid`; недостающее имя — `NotConfigured`); секреты только в окружении, не в аргументах. Провод stdio: запись и чтение в своих потоках с каналами (`recv_timeout(25 ms)` замечает флаг отмены и срок), строка stdout ограничена во время чтения 256 KiB (`take().read_until`), меньшие пределы операций (128/64 KiB) — по мере приёма с учётом уведомлений; мусор, слишком длинная строка, запрос сервера к клиенту — `Invalid`; конец потока и `EPIPE` записи — `Unavailable`. Любой отказ провода (срок, отмена, `Invalid`, `Unavailable`) останавливает процесс и помечает сервер `Failed`: дальше «недоступен» без перезапуска. Остановка: закрыть stdin, SIGTERM группе, ≤300 ms, SIGKILL группе, лидер ≤2 s, затем проба группы `test_kill_process_group` ≤2 s с SIGKILL только при живых участниках; не собранный лидер уходит фоновому потоку, группа не опустела — «остановка не подтверждена» (`LocalHost::finish` возвращает такие серверы, Drop останавливает всё на любом пути). Хвост stderr 8 KiB в памяти, точные значения секретов вырезаются, показывается только в обнаружении при отказе. `discover` — удалённый 20 s, локальный 120 s с запуском, отменяем флагом операции. Зависимость `rustix` 1.1.5 (`process`, только `cfg(unix)`). Тесты: `local_host_tests.rs` на тестовом сервере `tests/fixtures/stdio_server.py` (игнор конца stdin, игнор SIGTERM, внук в той же группе, мусор, длинная строка, молчание на `initialize`, ранний выход, запрос к клиенту, закрытый stdin/EPIPE, не читающий stdin при запросе 1 MiB, окружение, ≤4 процессов, неподтверждённая остановка, хвост stderr, отмена при запуске и вызове, разбор карты).

## MCP-клиент и шаги модели с инструментами (24A / ADR-021)

`mcp.rs` — собственный минимальный клиент MCP 2025-06-18 (без `rmcp`): каждая операция — `initialize` (без заявленных возможностей) → `notifications/initialized` → `tools/list` (≤3 страниц, ≤128KiB, ≤64 инструментов) и/или `tools/call` (≤256KiB) в пределе 20s; `Mcp-Session-Id` и `MCP-Protocol-Version` после инициализации; ответ JSON или SSE до сообщения с нашим id; запрос сервера к клиенту, `input_required`, некорректный или слишком большой ответ — `Invalid`; 401 — `LoginRequired`; `isError` и ошибка JSON-RPC — `ToolError`. При первом вызове сервера в запросе живые определения хэшируются функцией Core, и изменённый инструмент не вызывается. Отмена — флаг Core; закрытие соединения в 2025-06-18 не обязывает сервер остановиться (ограничение). reqwest без redirect/retry/proxy, свой runtime на операцию; `wait.rs` — один общий помощник ожидания с флагом отмены (заменил копии в `model.rs` и `integration.rs`). Loopback HTTP — только в тестах/test-support.

`model.rs`: `run_model_step` выполняет один допущенный POST цикла. `Plain` — прежнее тело побайтно (эталон `tests/fixtures/no-plugin-assistance-body.json`); `Tools` — инструменты одной `namespace` `plugins` (`type:function`, `strict:false`), инструкции о недоверенных результатах и ссылках `tool:N`, skills как помеченные подсказки, история (пересылаемые reasoning/`function_call` и `function_call_output`); `Final` — без инструментов. SSE-декодер в режиме инструментов принимает `function_call` (`call_id`, `name`, `arguments` ≤8KiB → объект) и события `response.function_call_arguments.*`; вызовы имеют приоритет над текстом. Предел тела с инструментами — 320KiB + 480KiB. Тест `actual_http_oversize_and_quota_errors_remain_bounded` больше не зависит от нагрузки (`target/verification/24a/flake-debugging.md`).

## Постоянный полный набор (08B / ADR-015)

Текущий assistance response — строгий объект `proposals` (0..16) и `rationale`. Каждый элемент имеет обязательные proposal_id (null либо ID из точного Continue preview), kind, message, rationale, evidence_ids и nullable step_id. Unknown/duplicate/missing fields, неверные nullable-типы и count/byte overflow отвергаются; silence — пустой массив. Core отдельно проверяет принадлежность/уникальность IDs, citations и готовность шага, затем атомарно публикует весь набор после прежнего ledger accounting.

Continue получает все прежние IDs, включая закрытые карточки, и атрибутированные пары. Instructions требуют сохранять ID того же действия и использовать null для нового; совпадение текста/оснований не служит дедупликацией. NewContext не передаёт старые предложения и пары. Reply содержит отдельно неподтверждённый model_question и точный user_reply; они не становятся Evidence, планом или разрешением действовать.

Endpoint/model/effort/tier/auth, одноразовый transport, deadline/cancellation/actual cleanup, known/unknown usage, SSE2MiB/frame512KiB/item64KiB, model JSON32KiB/context256KiB/body320KiB сохранены. Локальные HTTP/SQLite/Swift доказательства находятся в `target/verification/08b/`; настоящий Fast и semantic ID quality не проверялись.

## Bounded Responses transport (06D/06F)

`model.rs::run_model` потребляет non-clone `CheckDispatch` Core и выполняет максимум один POST на fixed `model_registry.rs::RESPONSES_ENDPOINT`. Connectivity выбирает фиксированный Luna Low/High Fast и точный `AMBIENT_OK`; assistance использует только High. Low прежний:256bytes результата. Нет произвольного endpoint/model/prompt в production ABI, org/project headers, max_output_tokens, retries, redirects, refresh или fallback. Bearer приходит от единственного native coordinator и не сохраняется.

Assistance получает только exact snapshot Core. Один strict `text.format/json_schema` с пятью обязательными полями kind/message/rationale/evidence_ids/step_id и additionalProperties=false; простые nullable поля без conditional keywords. Instructions рассматривают сохранённый текст как untrusted data и запрещают внешние факты/действия. Полный serialized body<=320KiB проверяется до dispatch; context<=256KiB. Оба назначения используют store=false/stream=true/tools=[] и priority. Requested не заменяет actual: каждый terminal проверяет Luna, выбранный low/high и actual priority/fast; default/absent/other — mismatch.

Refusal/incomplete/failed/malformed/quota — ошибки, не silence. Core отдельно проверяет смысл, grounds и readiness. ## Общий транспорт интеграций (23A)

`IntegrationTransport` — единственный HTTP-транспорт встроенных интеграций: reqwest без redirect/retry/proxy/cookie, connect5s/read10s, собственный current_thread runtime (удаляется до снятия занятости в Core), ожидание с флагом отмены Core срезами по25ms, общий срок `RequestBuilder::timeout(remaining)`, заголовки ≤32KiB после разбора с неоднозначностью по статусам реестра, тело только для200 с checked-счётом chunks. Форма секрета проверяется по виду до сети (Jira: email ≤254 без двоеточия и токен ASCII graphic ≤16KiB через `basic_auth`, заголовок помечен sensitive). Реестр адаптера (`jira_registry::REGISTRY`) задаёт фиксированные заголовки, извлекаемые заголовки ответа (Jira — только `retry-after`) и статусы 401/429/503; адрес строит `jira_registry::url`.
